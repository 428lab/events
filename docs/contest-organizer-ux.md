# イベント情報と運営管理の分離（Issue #541）

- 要件: [Issue #541](https://github.com/428lab/events/issues/541)。この文書が設計の正本。
- 最新の指示: **「イベントはイベントの情報だけ、運営関連は別の管理用ページに別れてて欲しいなあ。スタッフ以外にどう見えてるのかわからなくなるので」**。
- 状態: **上記の分離を実装し、独立レビュー後にstagingへ反映する方向は承認済み。この更新は実装前の設計修正のみ。** main/productionへの反映は含まない。
- 現行基準: stagingの `342cc35b34a54727fd74ce2663f4884dcc0e44c9`（PR #542/#543 はマージ済み）。main/productionは `ebadabce8fca6ea0fcef21fc5f6e9bdc82305ea2` のまま。以下は現行ソースの照合であり、認証済みstagingでの実機確認ではない。

## 1. 何を置き換え、何を維持するか

前案の「詳細上部にコンテスト運営カードを展開」「一般の運営ボタンは詳細に残す」「新ルートを作らない」は**撤回する**。詳細に管理カードを足すだけでは、運営自身が参加者向けの情報の並びを確認できない。

採用するのは **イベント詳細 `/events/:id` と管理入口 `/events/:id/manage` の分離**。詳細にはイベント情報・共通の参加操作と、小さな「管理」リンク一つだけを置く。管理はコンテスト専用ではなく、現に詳細にある一般運営業務の入口にもする。既存 `/control` はコンテストの進行・集計・賞編集専用であり、一般イベント用の管理入口に流用すると不要な採点取得や画面が混ざるため、置き換えない。

維持するもの:

- `ControlPage` に統合済みの `AwardsEditor`、集計、即時保存フィードバック、保存確認前の表彰切替/移動ガード。**賞・賞品・受賞者の編集は引き続き `/control#awards` 一か所だけ**。`EditEventPage` の移動先リンクも維持。
- 本人の参加/退出、入場QR、アンケート回答、日程投票、提出、採点、写真/コメント/Q&A/チャットの投稿と本人操作。staffであることだけを理由に通常の参加導線を消さない。
- 既存API・サーバー認可・参加条件・自己採点ルール・採点締切・モード/発表位置・保存/通知/同期の意味。新しいAPI、schema、DB、権限、ルール、鍵、リレー変更は不要。

参加者プレビュー、役割切替スイッチ、なりすまし、偽の `myRole`、共有ログインは作らない。これは画面の責務の分離であって、別人のデータを見る機能ではない。未参加者に会員情報を開示するなどして外見を揃えない。

## 3. 画面構成と普通のクリック経路

### イベント情報 `/events/:id`

```text
イベント画像 / タイトル / 開催日時                  [管理] ※権限があるとき一つだけ
状態・本人のロール / 共有 / カレンダー / 会場・人数
日程投票・公開結果、表彰結果、説明
ビンゴ・タイムテーブル・資料・交流（現在の順序/表示条件を維持）
参加・退出 / 本人QR・回答・提出・採点などの共通操作
写真 / コメント / 提出物
参加者一覧（デスクトップは既存サイドバー、狭い画面は下）
```

- staffにも同じ情報の階層を使う。上部にコンテストダッシュボード、運営ボタン群、招待カードを挿入しない。「管理」はタイトル付近の小さなリンク/ボタンとし、常駐バー等を増やさない。
- 現行 `EventActionButtons` の `!isStaff` による採点/発表/表彰/進行状態の除外と、`EventJoinPanel` のstaff採点案内除外は、旧カードへの集約のためだった。これを解消し、staffも本人の共通操作として詳細から採点等へ行けるようにする。締切や参加条件は既存判定のまま。
- 外見の共通化は公開情報の構成についてであり、本人の参加状態、下書き/非公開の閲覧可否、会員向け案内、取得可能データの差をなくすものではない。

### 管理 `/events/:id/manage`

```text
イベント名 / 管理                          [イベント情報へ戻る]
（下書きなら）公開前の案内 [公開]
コンテスト運営                              ※staffかつcontestModeのみ
  準備 [採点項目] [賞・賞品]
  エントリー・採点 [状況を見る] [自分で採点する]
    個人参加staffの採点対象スイッチ / [自分の提出物へ]
  賞・受賞者 [集計を見て受賞者を選ぶ]
  表彰式 [表彰式の準備・進行へ]
一般運営                                    ※staffのみ、既存リンクを折り返す
  [イベント編集] [配信] [一斉連絡] [TODO] [スタッフチャット] [持ち場]
  [景品引換] [ビンゴ管理] [事前アンケート管理] [統計] [受付] [名札] [チャット管理]
その場で管理                                ※必要な項目だけ開く
  日程調整 / タイムテーブル・資料 / 参加者 / 招待 / 会場オファー
  写真 / コメント / Q&A
```

- 初期表示は入口中心。既存ページがある業務はリンクだけ、埋め込み操作には見出し付き折りたたみを使い、**開いた対象部品だけをマウント**する。写真/コメント/Q&A等の公開コンテンツ全体を初期表示で複製する巨大ダッシュボードにはしない。既存表示条件で不要な項目は出さない。
- 表のhashで直接開くと該当項目が展開され、取得後に見出しへスクロール/フォーカスする。戻る操作でも同じ項目に戻れるよう通常リンクとURLを使う。コンテストカードは既存 `ContestOperationsSection` を再利用する。
- 非コンテストにも一般運営/埋め込み操作の移設を適用するが、コンテストカード・採点/賞関連の取得やフォームは出さない。個人/チーム、オンライン/会場等は現在使用中の条件を保つだけで、イベント種別の機能を増やさない。
- モバイルではページ先頭を「イベント名 / 管理」と明示し「イベント情報へ戻る」を直下に置く。リンクは縦積み/折り返し、折りたたみの見出しをタップ可能にする。情報ページとの区別を色だけに頼らない。既存MUI/`DESIGN.md`を使う。

普通の運営としての経路:

1. 詳細で参加者に案内する情報を見る →「管理」。
2. 「賞・賞品を設定」→ `/control#awards` で賞名/賞品を設定。同じページの集計から受賞者を選択し「保存済み」を確認。
3. 明示的に「参加者の画面を表彰式に切り替える」→「表彰式を開く」。遷移だけでは状態を変えない。
4. 管理へ戻る →「イベント情報へ戻る」。一般運営業務も詳細「管理」から既存ページ、または目的の折りたたみ一つへ。
5. 自分の採点は詳細の共通導線でも管理のコンテストカードでも可能。採点対象スイッチは管理のみ、本人の提出は管理から詳細 `#submissions` に戻って行う。

## 4. ルーティング・権限・戻り先

- `App.tsx` の認証済み側に `/events/:id/manage` → `EventManagePage` を一つ追加。**`EventLayout` の外、通常の `Layout` 内**に置く。理由は管理用入口には参加者モード強制遷移を適用せず、既存の非staffアクセス管理者も招待操作に到達させるため。`EventLayout` 自体や既存ページの強制遷移ルールは変更しない。未ログインの扱いは既存の認証済み専用ルートと同じ。
- 管理入口/ページの可否は `myRole === 'staff' || (event.visibility === 'private' && data.canManageAccess)`。読み込み完了前や取得失敗時は管理部品をマウントしない。無権限の直接URLには権限なしとイベント情報への戻りだけを表示する。
- **既存例外を承認確認済み:** `canManageAccess` はサーバーの `isEventManager` 判定で、staffだけとは限らない。非staffアクセス管理者には既存の非公開招待だけを表示し、公開・一般運営・コンテスト・モデレーションの権限を新たに与えない。staffでも非公開招待は従来どおり `canManageAccess` が必要。サイト管理者というだけで管理トップに一般運営を追加しない。
- `/control`、`/criteria`、`/awards` 等にある `useIsAdmin` の例外、サーバーの認可はそのまま。新しい管理UIは権限の根拠ではない。非staffの専用ページ管理者が `/manage` の条件を満たさない場合、従来のイベント/進行への戻りを残し、到達不能な管理リンクを出さない。
- 管理→詳細は `/events/:id`。`ControlPage` の旧「詳細のコンテスト運営へ戻る」は管理リンクへ変更。`CriteriaAdminPage` とstaffの `ScoringPage` も管理への戻りを明示する。`AwardsPage` は既存 `/control#ceremony`（保存・準備への戻り）を残し、条件を満たす運営には別途「管理へ戻る」を置く。既存 `/chat` もstaff向け管理戻りを明示する。通常の参加者には管理戻りを出さない。
- `/control#scoring/#awards/#ceremony`、`/criteria`、`/awards`、`/edit` 等の旧直接URLは廃止/一括リダイレクトしない。旧 `/events/:id#contest-operations` は詳細の小さな「管理」入口をアンカー対象にし、運営カードを復活させず移動先を見つけられるようにする。`#submissions` は維持。新しい画面遷移でPOST/PUTやmode切替を起こさない。

## 5. 部品の責務と実装順

実装前にこの文書をレビューし、続いて以下の単位で狭く変更する。

1. **入口とリンク:** `pages/EventManagePage.tsx` を新設し `App.tsx` に上記のルート/ガードを追加。`EventDetailPage` の管理カード・一般運営リンク・公開/招待/会場操作を移す。`EventActionButtons` は共通操作のみとし、移したリンク表は小さな `EventManagementLinks` 部品へ。`ContestOperationsSection` / `SelfEntryParticipation` のフォーム・hookは再実装しない。
2. **埋め込み操作:** 表の既存部品に必要な表示責務だけを追加する。例えば `showManagementActions` を詳細ではfalse、管理側ではtrueにし、**実際の `isStaff` / `myRole` / `canModerate` とANDで**操作を表示する。role値自体を偽装したり、falseだけで本人操作もまとめて消したりしない。専用ページの既存表示は維持し、変更の対象を詳細の呼び出しに限定できるようにする。
3. **運営専用情報と本人操作の分離:** `EventSchedule` / `EventMaterials` は詳細では `visibility === 'staff'` と `placement === 'unassigned'` を除く表示用集合を使い、列・時刻・資料件数にも反映する。編集側には全量を渡す。Q&Aも詳細の表示用集合だけで非表示質問を除き、匿名投稿者の実名表示を無効にする。サーバー応答/共有Queryキャッシュを書き換えず、管理には既存の許可された情報を残す。取得不能な情報を追加取得して同じ見た目にしない。
4. **チャットは既存ページを使う:** `EventChat` の詳細カードでは管理操作と `canOpenChannel` を表示用途で抑制し、通常の参加・送信の権限は実ロールのまま。開設待ち表示を揃え、管理から既存 `/chat` へ行く。`useChatChannel`、署名/同期/リレー処理は変更しない。
5. **戻り/文言:** `ControlPage` / `CriteriaAdminPage` / `ScoringPage` / `AwardsPage` / `EventChatPage` の戻り先と日英辞書を更新。情報・管理・コンテスト運営の見出しを区別する。リンク/hashは取得後も到達できるようにする。

その他の対象は上表の `EventMemberList`、`SchedulePanel`、`BingoCard`、`EventPhotos`、`EventComments`、`EventQa` 等と隣接テスト。巨大な詳細ページを管理ページにコピーしない。表示責務を分けるための小さな部品抽出はよいが、共通の権限フレームワークや全アプリのナビゲーション改修は不要。1ファイル800行の方針を守り、無関係な分割を行わない。

## 6. 維持する賞編集・表彰の契約

PR #543で実装済みの以下を壊さない。今回は配置と戻りリンクの変更で、保存実装の作り直しではない。

- 賞/賞品の追加・編集・削除・順位変更、受賞者選択は既存 `AwardsEditor` 一か所。受賞候補は既存entry（個人/チーム）であり参加者一覧を直接候補にしない。
- 受賞者は選択時、賞名/内容はblur時に保存。保存要求と再取得による確認までbusy。保存失敗は候補を保持して再試行/保存済みに戻す、保存後取得失敗はGETでのみ確認する。
- `useAwardEditorSave` と親の同期通知で、blur直後のクリック・並び替えの複数要求中・未解決の保存/取得失敗中は、表彰への切替と遷移を止める。取得失敗を「保存済み」にしない。
- 表彰切替は賞/進行状態取得済み・賞1件以上・保存問題なし・mode要求中でないことが必要。表彰を開くのはさらにmodeがawardsのときだけ。切替失敗を成功扱いせず、遷移は書き込まない。
- 採点締切や全賞割当を新たな必須条件にしない。未選択/該当者なしを自動補完しない。通常/プレゼン/集計操作、通知、表彰カーソル、発表リセットの意味は不変。
- `EditEventPage` に賞の実フォームを戻さない。保存済みcontestModeでだけ既存 `/control#awards` リンクを有効にし、未保存ON時の案内とイベント全体保存の意味を維持する。

## 7. 必要な検証・受入と今回の作業境界

**この設計修正で実施するのはソース/ルート照合と文書差分チェックだけ。** frontendコード、テストコード、リモートDB、配備は変更しない。既存PRの自動CIを回避しないが、設計のために全件テスト/手動CI/長いCI監視を行わない。

- `EventDetailPage` / `EventActionButtons` / `EventJoinPanel` と上表の部品の隣接テスト: 同じイベントのstaff/非staffで情報見出し順が同じ、管理入口は適切な権限に一つだけ。詳細に旧コンテストカード、公開、招待、編集、メンバーロール/出席更新、各モデレーション等の管理専用UIがない。本人の採点・提出・投票・投稿/削除・QR・回答等が残ることを肯定的に確認する。

- `ContestOperationsSection.test.tsx` と移設部品テスト: 管理内の採点対象スイッチ単一表示、既存リンク先/各条件、折りたたみとhash直行、情報への戻り、対象部品の管理操作が管理側に実在すること。管理UI非表示テストだけで「移した」としない。
