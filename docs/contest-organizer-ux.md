# コンテスト運営の導線整理（設計提案）

- 要件: [Issue #541](https://github.com/428lab/events/issues/541)
- 状態: **ユーザー承認済み・実装候補（独立レビュー前）。** 提案への「うん！」で実装とレビュー後のstaging反映を承認。追加要望「賞のせってもまとめてほしいな」により、賞・賞品の追加・名前・内容と受賞者選択を同じ「賞・受賞者」に集約する。設計PR: #542。本番/mainへの反映は含めない。
- 調査基準: `ebadabce8fca6ea0fcef21fc5f6e9bdc82305ea2`。main / staging / production のリモート参照が一致し、[PR #540](https://github.com/428lab/events/pull/540) のマージ先とも一致することを確認した。以下はこの版のソース調査であり、実ユーザーデータやセッションを使った画面検証ではない。

## 1. 目的と採用案

運営が「どこを押すか」「誰を選んでいるか」「保存できたか」を迷わず、準備から表彰式まで進めるようにする。

**イベント詳細に「コンテスト運営」をまとめ、既存の進行コントロールに既存の賞編集を移す。新しい管理画面・ルート・設定フォームは作らない。** 集計と受賞者選択を同じページに置き、保存完了を見て表彰式へ進む。賞の追加・内容編集・受賞者の選択は既存の `AwardsEditor` を一か所だけで利用する。

非対象: 採点計算・自己採点の可否・参加条件・権限、通知、ビンゴ、非公開イベントの基盤、同期の通信・鍵・リレー、表彰演出、イベントの作成仕様。受賞者の自動決定、採点の自動締切、移動だけでのモード切替は行わない。配色・書体は `DESIGN.md` と既存MUI部品を使う。

現在の代表的なクリック経路:

1. 詳細の混在ボタン群 →「進行コントロール」→ 集計を見る →「受賞者を設定」。
2. イベント編集の先頭へ到着 → 下へ探す → ランキング賞/特別枠の「受賞チーム」を選択（この時点で保存要求）。
3. 全体「保存」で詳細へ戻る、またはブラウザで戻る → 再び進行コントロール →「表彰モードにする」→「表彰式の操作へ」→「次を発表」。

「設定が存在しない」のではなく、配置・名前・保存フィードバック・戻り先が分断されている。

## 3. 提案する配置とクリック経路

### イベント詳細

staff かつ `event.contestMode` のときだけ、メインカラムの**タイトル/日時と下書き告知の直後、日程調整・説明・交流コンテンツより前**に一つのカードを置く。サイドバーには置かず、初期状態から展開する。一般の運営ボタンは既存位置のままにして、この依頼で全体ナビゲーションを作り直さない。

```text
コンテスト運営
  1 準備                 [採点項目を設定] [賞・賞品を設定]
  2 エントリー・採点     [エントリー・採点状況を見る] [自分で採点する]
    自分も採点対象として参加する  [スイッチ]  ※個人参加のstaffのみ
    自分の作品を採点対象に含めます。他の作品の採点とは別の操作です。
    （本人のエントリーがあるとき）[自分の提出物へ]
  3 賞・受賞者           [集計を見て受賞者を選ぶ]
  4 表彰式               [表彰式の準備・進行へ]
```

リンク先:

- 採点項目: `/events/:id/criteria`
- 賞・賞品 / 受賞者: どちらも `/events/:id/control#awards`（同じ編集欄。重複フォームを作らない）
- エントリー・採点状況: `/events/:id/control#scoring`
- 自分で採点: `/events/:id/scoring`。締切後も閲覧でき、採点欄の無効化は従来のまま。
- 自分の提出物: `/events/:id#submissions`。既存の本人フォームまでスクロールする。リンク表示は `myEntry` の有無で決め、個人以外の本人エントリーも妨げない。
- 表彰式の準備・進行: `/events/:id/control#ceremony`。**このリンクは状態を変えない。**

`EventSubmissions` のstaff用スイッチを小さな専用部品に移し、カード内だけで描く。表示条件・確認文・エラー・既存hookを維持する。提出フォームと提出一覧は移動/複製せず、そのままアンカーを付ける。

`EventActionButtons` からstaff向けのコンテスト3リンクとstaffの重複採点/表彰リンクを除き、カードへ集約する。進行中の状態表示もstaffはカード内に一つだけ表示する。発表中の「プレゼン画面へ」はカードの採点行に残す。非staffの「採点」、モード中の発表/表彰リンク、`EventJoinPanel` の「採点する」案内、提出フォームは従来どおり。staffの参加パネル内の採点案内だけカードの「自分で採点する」に集約し、同じ入口を再び増やさない。

### 既存 `/control` を「コンテスト運営」として整理

```text
イベントへのパンくず / コンテスト運営
[イベント詳細のコンテスト運営へ戻る]

1 準備
  [採点項目を設定] [賞・賞品を設定 ↓]

2 エントリー・採点                       #scoring
  エントリー N 件  [自分で採点する]
  発表の進行: 現在の状態 / 通常・プレゼン・集計 / 発表中の対象
  採点: 受付中 または 締切済み  [採点を締め切る / 採点を再開]
  採点者ごとの進捗                        ←既存の採点進捗
  エントリーごとの集計                    ←既存の集計プレビュー
  [集計を見て受賞者を選ぶ ↓]

3 賞・受賞者                       #awards
  受賞者は選ぶと保存されます。賞名・内容は入力欄を離れると保存されます。
  ランキング賞                           ←既存 AwardsEditor
    賞の名前 / 賞の内容 / 受賞者 [候補]  保存済み
  特別枠
    賞の名前 / 賞品・賞の内容 / 受賞者 [候補・該当者なし]
  [採点の集計へ ↑]
  [表彰式の準備へ ↓]

4 表彰式                                #ceremony
  受賞者設定 N / M 賞                     ←保存済みの割当数。完了判定ではない
  [受賞者を確認・変更 ↑]
  [参加者の画面を表彰式に切り替える]       ←明示的なモード変更
  [表彰式を開く]                         ←移動のみ
```

- 現在の集計テーブルを使い、エントリーを登録する別フォームは増やさない。Nは `entries.length`。0件なら「採点対象のエントリーはまだありません」と表示。採点者別進捗と採点対象の一覧を同じものとして数えない。
- 個人/チームに共通の新しい欄名を「受賞者」にする。個人なら名前、チームならチーム名を既存entry候補から表示する。参加メンバー一覧を直接候補にしない。
- 賞のない場合は `AwardsEditor` の追加欄を見せ、「まず賞を追加してください」を表彰式欄に添える。
- 既存上段のモードボタン群から表彰への切替を外し、表彰への切替は手順4に一つだけ置く。通常・プレゼン・集計の操作、発表対象の選択、採点の締切/再開は維持する。
- 採点中でも賞や受賞者は編集できる。採点締切を新たな必須条件にしない。表彰準備には現在の「採点は受付中 / 締切済み」を補足表示し、必要なら手順2へのリンクを置く。点数から受賞者を自動選択しない。
- 全賞への受賞者割当を必須にしない。未選択/該当者なしは既存仕様で発表できる。「受賞者未設定の賞は『該当者なし』として表示されます」と常設の短い補足にし、モーダル警告は増やさない。
- `EditEventPage` 内の `AwardsEditor` は外し、同じ位置に「賞・受賞者の設定はコンテスト運営で行います」と `/control#awards` へのリンクだけを置く。イベント基本情報の保存・キャンセルとは混ぜない。コンテストONを未保存のときは「イベントを保存すると設定できます」とし、リンクは保存済み `event.contestMode` がtrueのときだけ有効にする。

### 保存確認と、表彰式へ進める条件

新しい一括「保存」ボタンや下書き保存制度は作らない。既存の即時保存を見えるようにする。

| 操作・状態 | 表示・有効条件 |
| --- | --- |
| 受賞者を変更 | 既存PUTを一度送る。選んだ名前を欄に保持して「保存中…」。保存要求と賞の再取得が済むまで次の受賞者変更を無効にする（同じ編集画面での連打による上書き競合を避ける）。 |
| 保存成功 | 再取得した値で該当賞の割当を確認して「保存済み」。既存hookのinvalidateを利用し、取得失敗を成功表示にしない。集計欄/割当数にも保存済みデータだけを使う。 |
| 保存要求失敗 | 選んだ候補を消さず、欄の近くに「保存できませんでした」＋「再試行」「保存済みの内容に戻す」。候補は未保存と明記。再試行は同じ賞と候補へのPUT、戻すはGETで再取得するだけ。自動再送しない。 |
| 保存後の取得失敗 | 「保存内容を確認できませんでした」＋「再読み込み」。PUTを再送せずGETで確認。確認するまでは保存済みと扱わない。 |
| 賞名・賞品・追加・削除・順位変更 | 保存タイミングは維持し、エディター全体の「保存中…」/失敗表示を同じ仕組みで集約する。作成の失敗では入力欄を残し、削除等は成功済みと見せない。blurで開始する保存も直後の表彰ボタンの判定対象に含める。 |
| 「表彰式の準備へ」 | ページ内移動のみ。保存中/未解決の保存失敗・確認失敗時は無効にして「保存を確認してから進めます」。 |
| 参加者の画面を表彰式に切替 | 賞と進行状態の取得済み、賞1件以上、上記の保存問題なし、モード変更要求中でない場合に有効。すでに表彰中なら「表彰式に切替済み」と表示して無効。採点締切・全賞の受賞者設定は条件にしない。 |
| 表彰式を開く | `state.mode === 'awards'` かつ上記の保存問題なし、モード変更要求中でない場合に有効。切替前は「先に参加者の画面を表彰式に切り替えてください」を添える。遷移時にPUT/POST/PATCHを送らない。 |
| モード変更失敗 | その場に「表彰式に切り替えられませんでした。もう一度お試しください」。成功するまで遷移を有効にしない。勝手に再実行しない。 |

保存状態は `AwardsEditor` と親の `ControlPage` が扱う局所的な状態で十分。エディターから親へbusy/未解決エラーを伝え、**モード切替と遷移の両方で**参照する。クリックハンドラーでも最新の保存状態を確認し、blur→clickの順で保存が始まる場合にも素通りしない。順位変更は複数要求がすべて終わるまでbusyとする。保存失敗後に賞名/内容等を修正して再保存、またはサーバー値を再取得して戻せるようにする。未追加の賞名入力は「追加」前なので保存済み賞に数えない。新たな全画面離脱警告、ブラウザの戻るを封じる仕組み、複数端末の編集ロックは作らない。

**通常の新導線:** 詳細「集計を見て受賞者を選ぶ」→ 同じ進行画面で集計確認/手動選択 →「保存済み」→ 下の「参加者の画面を表彰式に切り替える」→「表彰式を開く」→「次を発表」。イベント基本情報の編集や保存を経由しない。

### 戻り先・スマートフォン

- 詳細カードに `id="contest-operations"`、提出に `id="submissions"`、進行の3箇所に上記idを付ける。React RouterのURL hashだけにスクロールを期待せず、取得後の描画とhash変更時に対象へスクロール/見出しフォーカスする。固定ヘッダー分の `scroll-margin-top` を取る。ブラウザバックで同じ位置へ戻れるよう、ページ内の通常リンクを使う。
- `CriteriaAdminPage` に「コンテスト運営へ戻る」→ `/control`。`ScoringPage` に同じ戻りリンクをstaffのみ追加。既存パンくずは維持する。
- `AwardsPage` の既存staff向け「進行コントロールへ戻る」を「受賞者・表彰の準備に戻る」→ `/control#ceremony` に変更。その先の「受賞者を確認・変更」で `#awards` へ戻る。参加者には運営へのリンクを出さない。
- 表彰画面の「リセット」は「発表を最初からに戻す」と表示し、既存のカーソルリセットを使う。受賞者や採点を削除する意味には変えない。「次を発表」の終了/保存待ち/演出待ちの無効条件、通知の条件、同期/演出は変更しない。
- 幅の狭い画面は4行を縦積み、各行のボタンも幅いっぱいで折り返す。横スクロールするステッパーや常駐下部バーは作らない。進行画面も単一カラム、見出しへの近道を上に置き、既存集計表だけ横スクロールのコンテナに入れる。順位賞の既存ドラッグ方式自体の改修は今回に含めない。
- 保存メッセージは該当欄の近くに置き、`aria-live="polite"`。色だけで保存状態を伝えない。日英の辞書を同時に更新する。

## 4. データ・権限・互換性の境界

- 新API・新テーブル・マイグレーションは不要。既存 `useAwards` / `useEventEntries` / 賞CRUD / `useSetAwardResult` / `useSetMode` / 採点hookを使う。
- 受賞者保存は `/api/events/:id/award-results` に `{ awardRankId, entryId }` または `{ specialAwardId, entryId }`。`entryId: null` は解除。返却 `{ ok: true }` の後、既存awards取得で表示を確認する。APIはstaff権限・同イベントの賞/entryを検証する（`apps/server/src/routes/awards.ts:158–189`）。ここを変更しない。
- mode変更は既存 `/state/mode`。mode変更はmodeだけを書き換えるため、締切・受賞者・発表カーソルを暗黙に変えない（`apps/server/src/db/repositories/eventState.ts:41–49`）。再び表彰に入ってもカーソルを勝手にリセットしない。
- 新しい詳細カードの表示は `myRole === 'staff' && contestMode` のみ。現在の各専用ページには `useIsAdmin` の例外も存在する。今回それを増減せず、既存のページ権限とサーバーの認可を維持する。staffでないアプリ管理者へ詳細カードを新設しない。
- コンテストでないイベントには新カード/新しい編集欄を出さない。既存の直接URLに対する認可・画面挙動の整理は別件とし、今回勝手に禁止/許可を増やさない。
- 参加者向け結果の公開条件（`EventAwards` の終了/発表済み判定、採点結果の締切/終了判定）、自己エントリー参加、採点集計、参加メンバーの確認条件は変更しない。
- 競合解決や権限失効を新たなフロントエンド基盤で扱わない。既存サーバー拒否はエラーとして表示し、ナビゲーションで再送/受賞者再設定をしない。フォーム状態は対象event/awardで分離し、別イベントの候補・保存エラーを持ち越さない。
- 既存URLは廃止せず、`/edit` に移動先を残す。復旧が必要な場合はUI変更を戻すだけで、データ移行の巻き戻しは不要。

設計時: 現行ソース・ルート・文言・保存処理の照合、文書差分チェックのみ。ローカル全件テストや手動CIは行わない。既存のPR自動CIは回避/変更しない。以下は承認後の実装に必要な検証であり、実行済みではない。

- `AwardsEditor.test.tsx` と `ControlPage.test.tsx` で候補選択→PUT→再取得→保存済み→明示的mode切替→純粋な遷移を確認。遅い保存・保存失敗・取得失敗・再試行、blur直後の表彰クリックを含め、保存完了前は表彰へ進めないことを検証。順位変更の複数保存待ちも扱う。
- 賞0件、entry0件、特別枠の該当者なし、採点受付中の手動割当、表彰から戻る/再開を確認。未選択の賞を勝手に補完せず、遷移で締切/カーソルが変わらないことを確認。

承認後、テスト用イベントで行う受入（実データを使わない）:

## 8. 実装候補の検証記録

- `AwardsEditor` は既存の進行画面だけで描画する。賞ごとの保存状態は専用の `useAwardEditorSave` に閉じ、共通の保存基盤や全画面ロックは追加しない。blur直後のクリックは親への同期通知でも止める。
- 保存成功後の取得失敗は書き込み失敗と区別し、再取得でのみ復帰する。保存済みに戻す操作ではエディター内のフィールドを再生成し、サーバーの値が変わらない場合も未保存入力を戻す。共通 `BlurCounterField` は変更しない。
- レビュー修正: 順位変更の全PATCHが失敗し、復旧GETが同じデータを返す場合も、取得結果からローカルの表示順を明示的に戻してから保存エラーを解除する。表彰への切替失敗メッセージは表彰モードへの変更時だけに限定し、通常・プレゼン・集計への操作は維持する。両不具合を対象テストで修正前に再現し、修正後は同ファイルの14件が成功。
- 保存・復旧・並び替え・表彰への接続を `ControlPage.test.tsx` で実hookとともに検証。スイッチの確認・拒否・取得待ちと表示条件は `ContestOperationsSection.test.tsx` に集約し、別名の重複テストは作らない。
- ローカルの隔離したWorker/D1と合成ユーザーで、デスクトップ/スマートフォン幅の実ブラウザ操作を実施。賞・特別枠の作成、名前・内容の編集、受賞者選択はすべて画面から行い、戻る/再読込後の永続化、採点受付継続、発表位置の保持を確認した。イベントと別の参加者の初期データのみ合成データを投入。実ユーザーや外部サービスの認証情報は使わない。
- 保存ガードを別コピーで外すと、blur直後のモード切替/遷移の2つのテストが失敗することを確認。型検査・Webビルドと対象テストを実施。既知の名札印刷テスト（21件期待に対して18件）は本件外で修正しない。
- これは本番データ・staging上の実機受入やリレー疎通の証明ではない。既存CIと独立レビューの結果を確認してからstagingへ進める。main/productionへは進めない。
