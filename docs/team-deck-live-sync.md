- 前提: チームのスライド (#658, `cb4c02a`, docs/team-participation.md「チームのスライド」)。

- オーナー要望 (2026-11-03): 「同時に編集してる時は最新を読み込まなくても、Nostr のリレーから
  独自のエフェメラルイベントを読み書きすることで同期するようにできない？」
- 関連: docs/event-signal.md（サーバー発の合図 kind 20078）、docs/staff-chat.md・
  docs/participant-encrypted-chat.md（グループ鍵＋NIP-44）、docs/nip70-protected-chat.md

## 0. オーナー向けの要約

1. 同じチームのスライドを開いているメンバーの画面どうしが、リレー経由で編集を直接送り合う。
   相手の変更は 0.2 秒ほどで自分の画面に出る。「最新を読み込む」は、通信が切れていたときの予備だけになる
2. 送る中身は「どのページの、どの要素を、どう変えたか」という小さな差分で、チームの合言葉（鍵）で暗号化する。
   リレーにも外の人にも読めない。鍵は、サーバーがそのときのメンバーにだけ渡す
3. 2人が同じ要素を同時に動かしたら、あとから操作したほうが残る。別々の要素なら、両方の変更が残る。
   文字は欄ごとに上書きする（同じ欄を同時に打つと、あとの人の文が残る。「同じところを編集するほうが悪い」）
4. 「いま ○○さんが編集中」と、その人が選んでいる要素の枠も出す。これも同じ通信で流す。サーバーへの問い合わせは増やさない
5. 保存は今までどおりサーバーに送る。自分で操作したタブだけが保存し、ぶつかったら自動で合わせ直して保存し直す
6. メンバーが減ったら、合言葉を作り直す。抜けた瞬間に開いていた画面には、残りの誰かが次に保存するか合図が届くまで、差分が届くことがある（オーナー了承済み）
7. 自分たちのリレー2台（r.kojira.io / x.kojira.io）で、実際に送れることを確かめた（§2）
8. 実装は4つの PR に分け、最初は設定でオフにしたまま出す（§11）

オーナーの判断（2026-11-03、決定済み。§12）: ①チームのスライドだけ（個人のスライドは対象外）
②抜けた人の画面を強制的に読み直させない ③文字は欄ごとの上書き（文字 CRDT は作らない） ④不適切な内容のチェックはしない。

## 1. 何を作るか / 作らないか

作る:

- チームのスライドの編集画面どうしで、編集の差分を暗号化したエフェメラルイベントで送り合う
- 同じ要素を同時に触ったときは、要素の欄ごとに「あとから操作したほうが勝つ」で合わせる。どの画面でも同じ結果になる
- 編集中のメンバーの表示（名前と選択中の要素）
- 通信できないとき（鍵が無い・リレーにつながらない・機能がオフ）は、今の動作（409 で止めて選ぶ）のまま

作らない:

- 文字の1字単位の同時編集（文字 CRDT）。テキスト要素は欄（`text`）ごとの上書き（§5.4、オーナー決定 Q3）
- 個人のスライドへの適用（オーナー決定 Q1。§9）
- 配信セット（LiveSet）の同時編集。同じ `lib/editor` を使っているが、今回は対象外（変更は任意の引数にして影響させない）
- 差分のサーバー保存・再送・リレーへの永続化。エフェメラルは流れて消える。追いつきは HTTP の取得で行う（§7）
- 「最後に書いた印」（marks）のサーバー保存。サーバーは今までどおりの DeckContent（＋並びの `pos`）だけを持つ（§5.2・§7.5）
- 不適切な内容のチェック（オーナー決定: 発表資料なので不要）

## 2. 実リレーで確かめたこと（2026-11-03）

`wss://r.kojira.io`・`wss://x.kojira.io`（strfry 1.1.2、NIP-11 の `supported_nips` に 42・70 あり、
`max_message_length` 262144）に対して、使い捨て鍵で次を試した（スクリプトは手元のみ。リポジトリには入れない）。

| 試したこと | r.kojira.io | x.kojira.io |
| --- | --- | --- |
| kind 21078（`["t", topic]` だけ）を AUTH 無しで送る | 受理（OK true） | 受理 |
| 購読中の別接続に届く | 届く | 届く |
| `["-"]`（NIP-70）付きを AUTH 無しで送る | 拒否 `auth-required: event marked as protected` | 同じ |
| 同じ鍵で NIP-42 AUTH してから `["-"]` 付きを送る | 受理 | 受理 |
| 送った後に張った REQ に、直近の分が返る | 返る（数分保持） | 返る |
| 100KB の content | 受理 | 受理 |
| 30件を連続で送る | 30件とも受理 | 30件とも受理 |

結論:

- 使い捨て鍵の署名で書ける。NIP-07 などの Nostr 鍵は要らない。Discord や Google でログインした人でも動く
- `["-"]` を付けるなら、その使い捨て鍵で AUTH する必要がある（§6.1: 専用の接続を使う）
- 遅れて購読を張っても直近分が返ってくる。当て方を冪等にし、重複を除く（§7）
- strfry は古い `created_at` のエフェメラルを拒む（`rejectEphemeralEventsOlderThanSeconds`、既定 60）。
  なので `created_at` は壁時計にする（§6.3）。PR3 でローカル strfry.conf の値も確かめる

## 3. 全体の形

```
メンバーA のタブ                          リレー（r / x）                     メンバーB のタブ
 編集 → 差分を作る → 150ms まとめる
       → NIP-44 で暗号化 → 使い捨て鍵で署名
       → kind 21078 ["t",topic]["-"] ───→  そのまま流す（数分だけ保持） ───→ 検証 → 復号 → 画面に反映
 心拍（編集中・選択。setTimeout の連鎖）──→                              ───→ 「A さんが編集中」
 自分の操作があったら 800ms 後に保存（PATCH, baseRevision）→ サーバー（D1）
```

- サーバーは差分を中継しない。鍵と宛先（topic）を配るのと、保存を受けるだけ。Workers の負担は増えない
- サーバーへの定期的な問い合わせ（ポーリング）は足さない（D-POLL-MIN。`noPolling.test.ts` を通す）

## 4. 鍵と宛先（サーバー）

### 4.1 配る場所

編集用の `GET /api/decks/:id`（チームのいまのメンバーだけが取れる。`deckEditableSql`）の応答に `sync` を足す:

```ts
sync: {
  kind: 21078,
  relays: string[],          // getChatRelays()（chat_relays 設定。既定 r / x）
  topic: string,             // 不透明な hex（4.3）
  key: { version: number, secret: string }, // 32 バイト乱数の hex。NIP-44 v2 の conversation key
  me: { userId: string, name: string },     // 差分に載せる「誰が」（表示用）
  signal: EventSignalSource | null,         // deck-sync の合図（4.4）。eventSignal.source(deckId, "deck-sync", rev)
} | null   // 機能オフ・サービス鍵なし・チームのスライドでない → null（今の動作）
```

- `PATCH /api/decks/:id` の 200 と 409 の本文にも `syncVersion: number | null` を足す（4.4）
- 公開の閲覧（`/api/public/decks/:slug`）には絶対に載せない。運営（見るだけ）にも載せない
- 時間で鍵を取り直す仕組み（以前の案の `sessionTtlMs`）は置かない。定期の取得は D-POLL-MIN に反する

### 4.2 鍵の作り方: 保存する乱数＋世代（採用）

| 案 | 良い点 | 困る点 |
| --- | --- | --- |
| HMAC(サービス鍵, deckId) で導く | 列が要らない | メンバーが抜けても鍵を替えられない（替えるには世代番号を保存することになり、結局列が要る）。サービス鍵を替えると全部ずれる |
| **乱数を保存し、世代番号を持つ**（採用） | 抜けたら作り直せる。スタッフチャットと同じ考え方 | 表が1つ増える |

`deck_sync_key(deck_id PK→deck ON DELETE CASCADE, version INTEGER, secret TEXT, created_at)` を、デッキごとに今の1行だけ持つ。
古い世代は残さない（今の鍵だけが有効、と単純にするため）。user を参照しないので、登録簿（userTables・mergeUsers）の対象外。

- 初めての `GET` で作る。**作るのも読むのも、編集できるかの判定と同じ SQL の中で行う**（N1）:
  `INSERT INTO deck_sync_key … SELECT … FROM deck d WHERE d.id = ? AND ${deckEditableSql("d")} ON CONFLICT DO NOTHING` のあと、
  `SELECT k.version, k.secret FROM deck d JOIN deck_sync_key k ON k.deck_id = d.id WHERE d.id = ? AND ${deckEditableSql("d")}` で読む
  （または `editable` を出す `findForEdit` の SELECT で鍵も一緒に読む）。判定と読み取りの間に「抜ける＋作り直し」が確定しても、抜けた人に新しい鍵は渡らない
- **作り直す（version+1、新しい乱数）のは、編集できる人が減りうるとき**。入っただけでは作り直さない。経路は2種類:
  1. **`entry_member` の行が消える経路は、トリガー1つで全部拾う**:
     ```sql
     CREATE TRIGGER deck_sync_key_rotate_on_member_delete AFTER DELETE ON entry_member
     BEGIN
       UPDATE deck_sync_key SET version = version + 1, secret = lower(hex(randomblob(32)))
        WHERE deck_id IN (SELECT id FROM deck WHERE team_entry_id = OLD.entry_id);
     END;
     ```
     対象（実コードで確認済み）: `teams.ts` の `leave`（`leaveTeamsSql`）・`assign(null)`、**別チームへの移動**
     （`join`・`assign(team)`・`setLeader` の `placeStatements` は「元のチーム」の行を消すので、`OLD.entry_id` が元のチームを指す）、
     0115 のトリガー経由（`event_member` が確定参加者でなくなる・消える: `membershipChange.ts`・`eventAccessExit.ts`・
     `eventMembers.setStatus / setRole / remove / cancel`・`memberSlotResults.ts`）、ユーザー削除の FK CASCADE。
     チームの削除は空のチームしか消せない（`teams.ts`）ので作り直し不要
  2. **行は消えないが `deckEditableSql` を通らなくなる経路は、同じ batch に明示の UPDATE を足す**:
     - 退会リクエスト（`accountDeletion.ts` の soft delete。`user.deleted_at` を立てるだけで行は残る）:
       その人がメンバーの全チームのデッキ
     - `teams.setTeamMode(false)`: そのイベントの全チームのデッキ
     - `events.update` で `contest_mode` が変わったとき: そのイベントの全チームのデッキ。
       `visibility` の変更では作り直さない（招待限定へ変えると、取消していない参加者の招待は自動で承諾になり、メンバーは見え続けるため。`eventVisibility.ts`）
     - **`revokeEventAccess`（`eventAccessExit.ts`）**: その batch に、対象の人がそのイベントで入っているチームのデッキを作り直す
       UPDATE を、`accessOperationGuard` 付きで明示的に足す。終わった招待限定イベントでは参加・エントリーの片付けが
       `(scheduling = 1 OR ends_at >= now)` で飛ばされ、`entry_member` が残ったまま招待だけ取り消される（`deckEditableSql` は通らなくなる）ため、トリガーでは拾えない
- 以前の版の「退会は作り直し不要」は誤り。soft delete では行が残るので、上の 2 で作り直す

PR2 のテストで、上の経路を1つずつ（FK CASCADE を D1 で動かす場合を含めて）`version` が進むことを固定する。

### 4.3 宛先（topic）

`HMAC(NOSTR_SERVICE_KEY, "eventer/deck-sync/v1:" + deckId + ":" + version)` の hex。
世代ごとに替えるので、抜けた人が開いたままの画面は、新しい世代の宛先をそもそも購読していない。
宛先は絞り込みのための目印で、権限ではない。読めるかどうかは鍵で決まる。

### 4.4 世代の切り替えを届ける（抜けた人の画面の限界）

トリガーからは合図を送れない。なので、次の3つで届ける（どれも定期の問い合わせではない）:

1. **保存の応答**: `PATCH` の 200・409 が今の `syncVersion` を返す。自分の世代より新しければ、`GET` を1回取り直して切り替える。
   残りのメンバーの誰かが次に保存した時点で、そのタブは必ず新しい世代に移る
2. **合図**: メンバーを変える経路（`teams.ts` のルート、参加の取消・状態変更、`setTeamMode`・`events.update`、退会）は、
   確定したあとで1つの補助関数 `publishDeckSync(eventId)` を呼ぶ。そのイベントの全チームのデッキへ、
   `deck-sync` の refetch 合図を1件のイベント（`t` タグを複数）で送る（`eventSignal.publishRefetch`、`deferBackground`、失敗しても無視）。
   `EventSignalRefetchTopic` に `"deck-sync"` を足す。購読の設定は `sync.signal`（4.1）。範囲は deckId
3. **差分の `v`**: 受け取った差分の世代が自分より新しければ、取り直す

世代を切り替えたタブは、自分の pending log を新しい宛先へもう一度送る（先に切り替えた相手が、古い宛先の op を受け取れないため）。

取り直しで `GET` が 403 になった画面（抜けた人）は、同期を止めて「このスライドはもう編集できません」と出す。保存も 403 で止まる（今と同じ）。
それでも、合図が届かず、残りのメンバーもまだ保存していないあいだは、抜けた人の画面に差分が届く。
**オーナー決定 Q2: これは受け入れる。作り直しのたびに全員の画面を強制的に読み直させることはしない。**

## 5. 差分（op）のモデル

### 5.1 時計

各タブは `clientId`（タブごとの乱数 8 バイト）と、ハイブリッド論理時計 `hlc = { t: ms, c: counter }` を持つ。
比較の順番は `(t, c, clientId)`。この順番が、どのタブでも同じ全順序になる（同点は clientId で必ず決まる）。

- 自分の操作: **op ごとに** 新しい時計を進める。`t = max(now, last.t)`、同じ t なら `c+1`。1つのバッチ内の op もそれぞれ別の hlc を持つ
- 受け取ったとき・当てたとき: 当てた印すべて（読み込み時の床の印を含む）で `last = max(last, mark)`（HLC の受信規則）
- 未来に大きくずれた時計（> now+60s）の差分は捨てる（§8）
- **クライアントの時計とサーバーの時刻（`updatedAt`）は比べない**

### 5.2 状態と「ぶつかったときの勝ち」

`DeckContent` の構造（slides[]・elements[]、要素は `deckElementSchema`）はそのまま。差分を当てる側だけが、次の「最後に書いた印」を持つ（メモリ上だけ）。

- 要素の欄ごと: `lww[slideId][elementId][field] = hlc`
- 要素の存在: `alive[slideId][elementId] = { hlc, alive: boolean }`（削除は印＝墓標を残す。後から来た古い更新で生き返らせない）
- ページの存在と背景: `alive[slideId]`、`lww[slideId]["@slide"]["background"]`
- 並び: ページの並び、ページの中の要素の並び（重なり順）は、**分数の位置キー `pos`**（fractional indexing の文字列）の欄として扱う。
  並べ替えは `pos` 欄の上書き1つになる。表示は `pos` で並べ、同じ値なら id 順

**`pos` は保存する**（以前の版の「保存しない・読み込みのたびに配列順から振る」は誤り。読み込んだ版が違うタブで値がずれる）:

- `deckSlideSchema`・`deckElementSchema` に任意の `pos: z.string().max(32).regex(/^[0-9A-Za-z]+$/).optional()` を足す
  （足さないと `updateDeckInput` の検証で黙って落ちる）
- `pos` を持たない id にだけ、読み込み時に配列順から決定的に振る（既存のデッキの初回だけ）。**取り直し・当て直しでは振り直さない**
- 保存するときは、配列を `pos`（同じなら id）順に並べて書く。なので公開ビューアは配列の順番を見るだけで変わらない
- **PR1 から、同期の有無に関係なく、どの編集の経路でも `pos` を最新に保つ**（同期しないタブの並べ替えが、同期するタブに並べ戻されないため）:
  - `lib/deckSlides.ts` の作る・複製する・並べ替えるコマンド（`newTextElement`・`newImageElement`・ページ追加・複製・`move`・`toFront`・`toBack`・`moveZ`）は、`pos` を書く
  - 編集画面は `pos` 順で描く
  - 保存する側は、配列の順と `pos` の順が食い違っていたら、配列の順から `pos` を振り直してから送る（最後の守り）
- 間に入れるキーは、両隣のキーから決定的に作る（`fractional-indexing` 相当の小さな自前実装か依存1つ。PR1 で決める）。長さは 32 字まで。
  超えそうなら、そのページの並びを振り直す op（`pos` の `el.set` 群）を自分のタブから出す

### 5.3 op の種類

```ts
type DeckOp =
  | { op: "slide.add", hlc, slideId, pos, background }
  | { op: "slide.remove", hlc, slideId }
  | { op: "el.add", hlc, slideId, element: DeckElement /* pos を含む */ }
  | { op: "el.remove", hlc, slideId, elementId }
  | { op: "el.set", hlc, slideId, elementId, fields: ElementFields }   // ElementFields: §8 の el.set スキーマ
  | { op: "slide.set", hlc, slideId, fields: { background?: string; pos?: string } }
  | { op: "title.set", hlc, title: string }
```

- 1回の送信（バッチ）は `{ v, clientId, userId, name, baseRevision, ops: DeckOp[] }`。op はそれぞれ自分の `hlc` を持つ
- 当て方: それぞれの欄は、届いた印が手元の印より新しいときだけ上書きする。削除と生存も同じ印で比べる
- **墓標の要素への `el.set`**: 欄の印は更新するが、要素を生き返らせない。保留キュー（§5.6）にも入れない
- Undo で消したページを戻すときは、`slide.add` と、そのページの要素それぞれの `el.add` を一緒に送る
- グループ（`groupId`）は要素の欄の1つとして扱う。まとめる・外すは、複数の要素への `el.set` になる
- 画像: アップロードは今までどおり HTTP（`PUT /api/decks/:id/images`）。返ってきた `src` を `el.set` で流す。画像の中身はリレーに載せない

### 5.4 文字

`text` は欄ごとの上書き（**オーナー決定 Q3: 文字 CRDT は作らない。同じ欄を同時に打ったら、あとの人の文が残る**）。
打っている人は 300ms ごとに `el.set {text}` を送る。
打っている欄が他人の更新で書き換わると打ちにくい。そこで、**自分がフォーカスしている文字欄には、他人の `text` を当てずに保留する**。
保留したものは、フォーカスが外れたときに印を比べて当てる。

### 5.5 編集画面との関係

- 画面の `content`（`DeckEditorPage` の state）は「当てた結果」。ローカルの操作は今までどおり `setContent` する。
  同期の層（`useDeckSync`）は、**基準の中身**（最後に送った・または当てた結果）と新しい `content` の差を
  `diffDeck(base, next) → DeckOp[]` で取り出して送り、基準を `next` に進める
- **受け取った差分を当てたら、同じ手順の中で基準も当てた結果に進める**。受け取った変更を自分の変更として送り返さない
- `applyOps` は、変えなかった要素・ページのオブジェクトをそのまま使い回す（同一性を保つ）。なので `diffDeck` の浅い比較で余計な op が出ない
- ドラッグ中は `content` が変わらない（制約: docs/slide-editor.md §3）。なので、指を離した1回だけが差分になる
- `applyOps(state, ops) → state` は純関数（`lib/deckSync.ts`。React に依存しない）

**Undo**（`useEditorHistory` はスナップショットを丸ごと持つ。そのまま戻すと他人の変更まで戻ってしまう）:

- `useEditorHistory` に任意の `setContentFromRemote(next, apply)` を足す。`apply` は**印を見ない射影**: 生きている状態に実際に当たった op だけを
  （負けた op は含めない）、値を無条件で書く。スナップショットに無い要素への op は飛ばし、`el.add`・`slide.add` は挿入する。
  印の表は生きている状態で当てた時点で更新済みなので、「印が新しいときだけ」の規則でスナップショットに当てると何も当たらず、Undo で他人の変更が戻ってしまうため
  1. まず、自分のまだ確定していない手順（500ms のまとめ待ち）を確定する
  2. Undo と Redo の全てのスナップショットと `lastCommitted` に、同じ `apply` を当てる（純関数なので安全）
  3. 画面の `content` を `next` にする。この変更は履歴に積まない
- こうすると、Undo で戻るスナップショットにも他人の変更が入っているので、戻るのは自分の操作だけ。戻した結果は、ふつうの変更として差分になって送られる
- 引数は任意なので、`LiveSetEditorPage` は今までどおり動く
- PR3 の試験に「A が x を変え、B が y を変え、A が Undo → y は残る」を入れる

### 5.6 収束の理由（短く）

- 全ての状態は「欄 → (値, 印)」の集まり。生存も並び（`pos`）も欄。印は全順序の HLC で、op ごとに別の印
- 当て方は「印が大きいほうを残す」だけなので、可換・結合的・冪等。同じ op の集合を受け取ったタブは、どの順でも同じ状態になる
- `pos` は保存されて全タブで共有されるので、読み込んだ版が違うタブでも、同じキーは同じ位置を指す（§5.2）
- 欄が欠けたまま要素が届くことはない。`el.add` は要素の全体を持つ。`el.set` が `el.add` より先に届いたとき（生存の印も墓標も無い）は、
  保留キュー（最大 500 op・30 秒）に入れ、`el.add` が来たら当てる。30 秒を過ぎた保留は捨てて、HTTP の取り直しを1回予約する
- 同時の `slide.remove` で、ページが0枚になることがある。画面は「ページがありません」と「ページ追加」を出して戻せるようにする
  （ローカルの「最後の1枚は消せない」の制限はそのまま）

## 6. 送り方（クライアント）

### 6.1 接続

`ChatRelayPool`（`lib/nostrChat.ts`）の仕組みを使うが、**`signalHub` とは別の、同期専用の接続**を作る。
NIP-70 では、AUTH に使う鍵と送るイベントの署名鍵が同じでなければならない。`signalHub` の接続は自分の乱数鍵で AUTH するので共有できない。
同期専用の接続は、タブの使い捨て鍵で署名し、AUTH にも同じ鍵で応じる。

購読は `{kinds:[21078], "#t":[topic], since: now-120s}`。`authors` は付けない（送り手はメンバーごとの使い捨て鍵で、前もって分からない）。
今の `subscribeSignal` は `authors` を必ず付け、`since` を持たないので、PR3 で「`authors` 無し・`since` あり」の購読を足す。
世代が変わったら、古い購読を閉じて新しい topic で張り直す。

### 6.2 kind

**21078** を使う。エフェメラル（20000–29999）の範囲で、20078（サーバー発の合図）とは用途を分けるために別の kind にする。
NIP の登録表で 21059（Ephemeral Gift Wrap）・22242・23194/5・24133・24242・27235・28934–6 と重ならないことを確かめた。
既存の 27888（鍵の所有証明）・9807（グループチャット）とも別。

### 6.3 イベントの形

| 項目 | 値 |
| --- | --- |
| kind | 21078 |
| pubkey | タブの使い捨て鍵（同じタブでは同じ。「誰が」は中身で示す） |
| tags | `["t", topic]`, `["v", version]`, `["-"]`（NIP-70。使い捨て鍵で AUTH して送る。§2 で受理を確認） |
| content | NIP-44 v2（鍵は `sync.key.secret`）で暗号化した JSON: 差分のバッチ（§5.3）、または心拍 `{ clientId, userId, name, presence: { selected: string[], slideId, editingText?: elementId } | null }` |
| created_at | **壁時計** `floor(Date.now() / 1000)`（`hlc.t` ではない。strfry が古い時刻のエフェメラルを拒むため） |

`["-"]` を付けるのは、読めた人が別のリレーに持ち込むのを止めるため。中身は暗号文なので、漏れても読めない。ほかのチャットと同じ方針にそろえる。

### 6.4 間合いと大きさ

- 差分は 150ms まとめて1件にする。暗号化前の大きさが 32KB を超えたら、op の切れ目で分ける
- 1つの op だけで暗号化前 60KB を超えるとき（10,000 字の文字に制御文字が多い場合など。NIP-44 v2 の平文の上限は 65,535 バイト）は、
  その op は送らず、代わりに「取り直して」という短いバッチ（`ops: []`, `refetch: true`）を送る。受け取った側は、相手の保存のあとで `GET` を1回取り直す
- 暗号文の上限は同期専用の定数（`DECK_SYNC_CIPHERTEXT_MAX`、例 90KB）にする。`groupChatCrypto.CIPHERTEXT_MAX`（4096）は使わない。
  鍵の扱い・v2・版のタグの形だけを `groupChatCrypto` から流用する
- 心拍は 2 秒ごと、ただし選択や編集中の欄が変わったらすぐ送る。**`setInterval` は使わず `setTimeout` の連鎖**にする（`noPolling.test.ts` の対象外にするため。
  心拍はサーバーへの問い合わせではない）。タブが隠れているあいだは送らない。`pagehide` で「離れた」（`presence: null`）を1回送る
- 受け取った心拍は、6 秒届かなければ「編集中」から外す
- 送信は1タブあたり 1 秒に 10 件まで。超えたら、まとめる間隔を延ばす
- 受信側も `clientId` ごとに 1 秒 20 件までしか当てない。超えた分は捨てて、取り直しを1回予約する（悪意のあるメンバーによる描画の嵐を止める）

## 7. 追いつき・取りこぼし・保存

### 7.1 読み込み

- HTTP の `GET` で中身と `revision` を受け取る。`pos` の無い id にだけ `pos` を振る（§5.2）
- 全ての欄と生存の印を**床の印** `FLOOR = { t: 0, c: 0, clientId: "" }` で初期化する（どの本物の印にも負ける）
- そのあと購読を張る。リレーが返す直近分は**すべて当てる**（印を比べるだけなので冪等。`updatedAt` で捨てたりしない）

### 7.2 重複

`(clientId, hlc)` を受け取り済みの集合（直近 2,000 件）に入れ、2回目は捨てる。当て方そのものが冪等なので、集合はただの節約。

### 7.3 未保存の op の記録（pending log）

- 自分のタブが出した op は、**それを含むスナップショットの保存が成功するまで**、手元の記録（pending log）に残す
- `useDeckSave` がスナップショットを取るとき、そのときの記録の位置を一緒に覚える。保存が成功したら、そこまでを記録から消す
- 受け取った他人の op は記録しない（それは相手のタブの責任）

### 7.4 取り直し（切断・スリープ・合図・`refetch`）と当て直し（409）

取り直した中身（＝サーバーの最新）と手元の状態を合わせる。**直前に「途切れ」があったかで2通り**に分ける。
途切れ = 切断・スリープ（再接続）、`deck-sync` などの合図による取り直し、`refetch` の依頼、保留キューの期限切れ（§5.6）。

**A. 途切れのあと（取り直しすべて、と途切れのあとの 409）: 取り直した中身が勝つ**

1. このタブの pending log が触っていない欄と生存のフラグは、すべて取り直した中身の値にし、印を床の印に戻す
   （手元の値が他人の op 由来でも入れ替える。途切れのあいだに、もっと新しい保存があったかもしれないため）
2. 取り直した中身にあって手元に無い id は、床の印で足す（`pos` は中身のものを使う。振り直さない）
3. pending log の op を、もう一度当てる
4. 新しい `revision` を `baseRevision` にする

**B. 途切れの無い 409（読み込み以降ずっと受信できていて、メモリ上の印がそろっている）**

1. メモリ上の印と墓標はそのまま残す
2. 欄ごとに、手元の印が床の印のままのものだけ、取り直した中身の値に入れ替える
3. 取り直した中身にあって手元に無い id は、床の印で足す。手元の墓標があればそちらが勝つ
4. pending log の op を、もう一度当てる
5. 新しい `revision` を `baseRevision` にする

どちらも、**合わせた結果は「受け取った変更」の経路で画面に入れる**: 同期の層の基準を合わせた結果に進め、
`history.setContentFromRemote`、`useDeckSave` の `acceptRemote`（`latest`）を通す。`diffDeck` には掛けず、pending log にも入れない
（掛けると取り直した値が新しい印の自分の op として全タブへ流れ、もっと新しい値を上書きしてしまう）。

こうすると、自分の未保存の op は必ず残る。B では、受信できていた他人の op も残る。A では、受信したかどうかに関係なく、
サーバーに保存済みのものが勝つ（途切れのあいだに受け取れなかった op は、それを出したタブの保存か次の op で戻る）。

### 7.5 残る限界（オーナー決定 Q3 と同じ考え方）

印はメモリにしか無い。なので、**ページを読み直したタブ**は全ての欄が床の印から始まり、読み直す前に流れていた op と、
保存済みの値との「どちらが新しかったか」を正確には知らない。読み直したタブは保存済みの値を持ち、その後に届く op はすべて勝つ。
読み直しをまたいだ「あとから操作したほうが勝つ」は、おおよそになる。同じ欄をほぼ同時に触ったときだけの話で、
オーナーの「同じところを編集するほうが悪い」の範囲として受け入れる。途切れのあとの取り直し（§7.4 A）も同じで、保存済みの値に寄せる。正確にしたいなら、印を保存する（不透明な `sync_meta` を同じ PATCH で書く）案があるが、今回は採らない。

### 7.6 保存（`useDeckSave` の変更）

自分の操作があったタブだけが保存する。受け取った変更だけでは保存しない。`useDeckSave` に次を足す:

- `acceptRemote(nextContent)`: 受け取った変更を当てた中身を渡す。**`setContent` に渡したのと同じオブジェクトを、次の描画より前に**渡す（でないと保存の effect が新しい中身と見て保存を予約する）。`latest === ack`（自分の未保存が無い）なら、`latest` と `ack` を両方進める（保存しない）。
  未保存があるなら `latest` だけ進める（次の保存に他人の変更も入る。それは正しい）
- 409 の当て直し: 今の `reset`（中身を保存済み扱いにする）は使わない。キューを残したまま §7.4 で合わせ、`latest` を当て直した結果にして送り直す。
  回数は 3 回まで、間隔を延ばしながら（例 0.5・1・2 秒）。それでも 409 なら、今の 409 の案内（最新を読み込む・コピー）に戻る
- 保存の 400（中身の検証で弾かれた）は「スライドの上限を超えています（ページ300・要素200 など）」と、何が原因かを出す（§8）
- `baseRevision` が変わるのは、**このタブ自身の PATCH の応答か GET の応答だけ**。心拍に載せる `savedRevision` は「最後に保存: ○○さん」の表示にだけ使い、`baseRevision` には使わない
- 同期が無い（`sync: null`・リレー未接続で 10 秒以上たった）ときは、今の 409 の案内のまま

3つのタブで同時に編集しても、保存するのは操作したタブだけで、409 が出ても当て直しで収まる。409 の嵐にならないことを実地で確かめる（§10）。

## 8. 安全

- 鍵を持つのは、今のメンバーのタブだけ（`GET` が `deckEditableSql` を通るときだけ渡す）。鍵を持たない人は読めない。書いても NIP-44 の認証付き暗号で弾かれる
- 鍵が漏れた場合（メンバーが外に貼るなど）、外の人は次の作り直しまで、メンバーの画面に差分を送り込めるうえ、**編集の流れを読める**。
  ただし保存は、今までどおり HTTP でメンバー本人の権限で行う。被害は「メンバーの画面に変な変更が入り、気付かずに保存される」ことと、編集中の中身が見られることまで。メンバーを外せば鍵が替わる
- **当てる前の検証は、op の形だけを見る（手元の状態を見ない）**。状態で判断すると届いた順で結果が変わり、収束が壊れるため:
  - `slideId`・`elementId`: 1〜64 字。`pos`: §5.2 の正規表現・32 字まで
  - `el.add.element`: `deckElementSchema.strict()` に `pos` を足したもの
  - `el.set.fields`: `deckElementSchema.omit({ id: true, type: true }).partial().strict()` に `pos` を足したもの（id や種類は変えられない）
  - `slide.add`・`slide.set`: `background` は 50 字まで。`title.set`: trim して 120 字まで（`updateDeckInput` と同じ）
  - 未来に 60 秒以上ずれた `hlc` は捨てる。自分の世代と違う `v` は当てない（新しければ取り直す、§4.4）
  - 暗号文が `DECK_SYNC_CIPHERTEXT_MAX` を超えるものは、復号せずに捨てる
- **数の上限（ページ 300・ページあたり要素 200）は、自分のタブで作るときだけ**守る（今の画面の制限）。届いた op では捨てない。
  2人が同時に 199 個目を足して 201 個になったら、保存が 400 になり、上の具体的な案内が出る。消せば保存できる
- `userId`・`name` は中身にあるだけで、署名で保証されていない（同じ鍵を持つメンバーなら偽れる）。表示（「○○さんが編集中」）にだけ使い、権限には使わない。
  保存の「最後に保存: ○○さん」は、今までどおりサーバーが記録する
- 届いた `el.set`・`el.add` の `src` は、そのデッキの画像の URL（`/api/decks/<deckId>/images/…`）か、すでにその要素が持っていた値のときだけ当てる。
  送り込まれた op でメンバーのブラウザに外の URL を読ませないため（手で URL を入れる今の機能は、自分のタブの操作なので影響しない）。
  その代わり、手で入れた外の画像 URL は、ほかのタブでは次の取り直しまで前の画像のまま見える。これは受け入れる
- リプレイ: 同じ差分を送り直されても、当て方が冪等なので状態は変わらない。昔の差分を送り直されても、印が古いので負ける

## 9. 個人のスライドには使わない（オーナー決定 Q1）

対象は**チームのスライドだけ**。個人のスライド（同じ人が別のタブ・別の端末で開く）は、今の 409 の案内のまま。
鍵の配布・作り直しの経路は、チームのメンバーの増減に結び付けて設計している。

## 10. 試験

- 単体（純関数・`lib/deckSync.ts`）:
  - 収束: ランダムな op 列を3つのタブに、異なる順番・重複・取りこぼしのあとの取り直しで当てる → 同じ中身になる（性質テスト、数百通り）
  - **読み込んだ版が違うタブ**（rev 3 と rev 5 から始めて、それぞれ間に挿入）でも同じ並びになる
  - 同じバッチで `el.add` のすぐ後に `el.set`（同じ要素）→ 全タブで同じ結果
  - LWW の境界: 同じ欄・同じ `t` で `c` や clientId が違う／削除と更新が同時（墓標は生き返らない）／並べ替えと削除が同時
  - `diffDeck` → `applyOps` で往復すると元に戻る。`applyOps` は変えなかった要素の同一性を保つ
  - §7.4 の当て直し: B（途切れ無しの 409）では他人の op も自分の未保存の op も消えない。
    A（途切れのあと）では、自分の pending log 以外は取り直した中身の値になる（例: 他人の f=1 を受けたあと途切れ、別の人が f=2 を保存 → 取り直すと f=2）
  - 合わせた結果を当てても `diffDeck` から op が出ない（受け取った変更の経路）
  - 検証: `id`・`type` を変える `el.set`、上限を超える文字列、未来の hlc は弾く。数の上限は届いた op では弾かない
  - 文字欄のフォーカス保留
- サーバー: `GET` の `sync` はメンバーにだけ出る（運営・外の人・公開の閲覧には出ない）。§4.2 の全経路で `version` が進む
  （トリガー: 抜ける・外す・移動・参加取消・状態変更・ロール変更・ユーザー削除の CASCADE。明示: 退会の soft delete・`setTeamMode(false)`・
  `contest_mode` の変更・**終わった招待限定イベントでの `revokeEventAccess`（参加者の行が残る場合）**）。`visibility` の変更では進まない。
  鍵は編集できるときだけ作られ・読まれる（判定と同じ SQL）。PATCH の 200・409 に `syncVersion` が出る。`deck-sync` の合図が出る
- 画面: 2〜3 のタブを模した結合テスト（同期の層を差し替え可能な送受信でつなぐ）:
  - 片方の操作がもう片方に出る。受け取った変更は送り返されない
  - **A が x を変え、B が y を変え、A が Undo → y は残る**
  - 受け取った変更だけでは保存しない。409 は当て直して保存し直す（3 回までのあと案内）
  - 3 タブで同時に操作しても、409 が続かない
  - `LiveSetEditorPage` の既存テストがそのまま通る
- 実地（必須）: ローカルの strfry を docker で立てる（本番と同じ版、`rejectEphemeralEventsOlderThanSeconds` を確かめる）。
  Playwright は**どの package.json にも入れず**、今までの e2e と同じく作業用の外部スクリプトとして使う（`/auth/dev-login` で2ユーザー）。次を確かめる:
  - 同時に動かす、並べ替える、文字を打つ
  - 片方を切断して再接続する。**読み込んだ版が違う2タブ**で間に挿入する
  - 片方の時計をずらす（ブラウザの時刻を数秒ずらす）
  - 相手が編集中に Undo する
  - **3 タブ**で同時に操作して、409 の嵐にならない
  - 片方をチームから外す: `teams` の「抜ける」と、**参加の取消（トリガー経由）**の両方。世代が切り替わり、外れた側が止まる
  - スマホ幅とPC幅で、「編集中」の表示を撮る
  - ステージングでは r / x を使う

## 12. オーナーの判断（2026-11-03、決定済み）

- **Q1 個人のスライド**: 対象外。チームのスライドだけ（§9）
- **Q2 抜けた人の画面**: 鍵を作り直し、保存の応答と合図で残りのメンバーを新しい世代に移す。
  それまでの短いあいだ、抜けた人の画面に差分が届くことは受け入れる。全員の画面を強制的に読み直させることはしない（§4.4）
- **Q3 文字の同時編集**: 欄ごとの上書きと、フォーカス中の保留（§5.4）。文字 CRDT は作らない。同じ欄を同時に打ったら、あとの人の文が残る
- **不適切な内容のチェック**: しない（発表資料のため）
