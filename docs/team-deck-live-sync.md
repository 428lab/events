## 0. オーナー向けの要約

1. 同じチームのスライドを開いているメンバーの画面どうしが、リレー経由で編集を直接送り合う。
   相手の変更は 0.2 秒ほどで自分の画面に出る。「最新を読み込む」は、通信が切れていたときの予備だけになる
2. 送る中身は「どのページの、どの要素を、どう変えたか」という小さな差分で、チームの合言葉（鍵）で暗号化する。
   リレーにも外の人にも読めない。鍵は、サーバーがそのときのメンバーにだけ渡す
3. 2人が同じ要素を同時に動かしたら、あとから操作したほうが残る。別々の要素なら、両方の変更が残る。
   文字は欄ごとに上書きする（同じ欄を同時に打つと、あとの人の文が残る）
4. 「いま ○○さんが編集中」と、その人が選んでいる要素の枠も出す。これも同じ通信で流す。サーバーへの問い合わせは増やさない
5. 保存は今までどおりサーバーに送る。全員の画面が同じ中身になるので、誰が保存しても同じ結果になる
6. メンバーがチームを抜けたら、合言葉を作り直す。ただし、抜けた瞬間に開いていた画面には、閉じるか合言葉が切り替わるまで届くことがある
7. 自分たちのリレー2台（r.kojira.io / x.kojira.io）で、実際に送れることを確かめた（§2）
8. 実装は4つの PR に分け、最初は設定でオフにしたまま出す（§11）

決めてほしいこと（§12）: ①個人のスライド（同じ人の別タブ）にも効かせるか ②抜けた人の扱い（すぐ鍵を替えるだけでよいか）。

## 1. 何を作るか / 作らないか

作る:

- チームのスライドの編集画面どうしで、編集の差分を暗号化したエフェメラルイベントで送り合う
- 同じ要素を同時に触ったときは、要素の欄ごとに「あとから操作したほうが勝つ」で合わせる。どの画面でも同じ結果になる
- 編集中のメンバーの表示（名前と選択中の要素）
- 通信できないとき（鍵が無い・リレーにつながらない・機能がオフ）は、今の動作（409 で止めて選ぶ）のまま

作らない:

- 文字の1字単位の同時編集（文字 CRDT）。テキスト要素は欄（`text`）ごとの上書き（§5.4）
- 個人のスライドへの適用（§12 Q1 次第。既定は対象外）
- 配信セット（LiveSet）の同時編集。同じ `lib/editor` を使っているが、今回は対象外
- 保存・再送・リレーへの永続化。エフェメラルは流れて消える。追いつきは HTTP の取得で行う（§7）
- 不適切な内容のチェック（オーナー判断: 発表資料なので不要）

## 2. 実リレーで確かめたこと（2026-11-03）

`wss://r.kojira.io`・`wss://x.kojira.io`（strfry 1.1.2、NIP-11 の `supported_nips` に 42・70 あり、
`max_message_length` 262144）に対して、使い捨て鍵で次を試した（スクリプトは手元のみ。リポジトリには入れない）。

| 試したこと | r.kojira.io | x.kojira.io |
| --- | --- | --- |
| kind 21078（`["t", topic]` だけ）を AUTH 無しで送る | 受理（OK true） | 受理 |
| 購読中の別接続に届く | 届く | 届く |
| `["-"]`（NIP-70）付きを AUTH 無しで送る | 拒否 `auth-required: event marked as protected` | 同じ |
| 同じ鍵で NIP-42 AUTH してから `["-"]` 付きを送る | 受理 | 受理 |
| 送った後に張った REQ に、直近の分が返る | 返る（数分保持） | 返る |
| 100KB の content | 受理 | 受理 |
| 30件を連続で送る | 30件とも受理 | 30件とも受理 |

結論:

- 使い捨て鍵の署名で書ける。NIP-07 などの Nostr 鍵は要らない。Discord や Google でログインした人でも動く
- `["-"]` を付けるなら、その使い捨て鍵で AUTH する必要がある。`ChatRelayPool` はリレーから AUTH を求められると、送信と同じ鍵で応じる仕組みを既に持っている（#464）。なので付ける（§6.3）
- 遅れて購読を張っても直近分が返ってくる。なので、受け取った分の重複を除くことと、古い分を捨てること（§7）が必須
- 大きさと連投の上限は、この用途では問題にならない。それでも送信側で上限を設ける（§8）

## 3. 全体の形

```
メンバーA のタブ                          リレー（r / x）                     メンバーB のタブ
 編集 → 差分を作る → 150ms まとめる
       → NIP-44 で暗号化 → 使い捨て鍵で署名
       → kind 21078 ["t",topic]["-"] ───→  そのまま流す（数分だけ保持） ───→ 復号・検証 → 画面に反映
 2秒ごとの心拍（編集中・選択）────────→                                ───→ 「A さんが編集中」
 800ms 後に保存（PATCH, baseRevision）→ サーバー（D1）
```

- サーバーは差分を中継しない。鍵と宛先（topic）を配るのと、保存を受けるだけ。Workers の負担は増えない
- サーバーへの定期的な問い合わせ（ポーリング）は足さない（D-POLL-MIN）

## 4. 鍵と宛先（サーバー）

### 4.1 配る場所

編集用の `GET /api/decks/:id`（チームのいまのメンバーだけが取れる。`deckEditableSql`）の応答に `sync` を足す:

```ts
sync: {
  kind: 21078,
  relays: string[],          // getChatRelays()（chat_relays 設定。既定 r / x）
  topic: string,             // 不透明な hex（4.3）
  key: { version: number, secret: string }, // 32 バイト乱数の hex。NIP-44 v2 の conversation key
  me: { userId: string, name: string },     // 差分に載せる「誰が」
  sessionTtlMs: number,      // 鍵の確認を取り直すまでの目安（4.4）
} | null   // 機能オフ・サービス鍵なし・チームのスライドでない → null（今の動作）
```

公開の閲覧（`/api/public/decks/:slug`）には絶対に載せない。運営（見るだけ）にも載せない（編集しないので要らない）。

### 4.2 鍵の作り方: 保存する乱数＋世代（採用）

| 案 | 良い点 | 困る点 |
| --- | --- | --- |
| HMAC(サービス鍵, deckId) で導く | 列が要らない | メンバーが抜けても鍵を替えられない（替えるには世代番号を保存することになり、結局列が要る）。サービス鍵を替えると全部ずれる |
| **乱数を保存し、世代番号を持つ**（採用） | 抜けたら作り直せる。スタッフチャットと同じ考え方 | 表が1つ増える |

`deck_sync_key(deck_id PK→deck ON DELETE CASCADE, version INTEGER, secret TEXT, created_at)` を、デッキごとに今の1行だけ持つ。
古い世代は残さない。抜けた人に古い差分を読ませないためではない（エフェメラルなので後から読めるものはもともと無い）。今の鍵だけが有効、と単純にするため。

- 初めての `GET` で作る（`INSERT … ON CONFLICT DO NOTHING` のあと読む）
- **作り直す（version+1、新しい乱数）のは、チームのメンバーが減ったとき**: チームを抜ける、運営が外す、参加を取り消す、退会、統合で負けた側、チーム参加をオフにする、チームが消える。入っただけでは作り直さない。
  チームの書き込み（`teams.ts` の batch）に `UPDATE deck_sync_key SET version=version+1, secret=? WHERE deck_id=(SELECT id FROM deck WHERE team_entry_id=?)` を同じ batch で足す。経路の一覧は `entry_member` から行が消える全ての場所で、実装時に grep で列挙してテストで固定する
- アカウント統合と削除: user を参照しないので、登録簿（userTables・mergeUsers）の対象外

### 4.3 宛先（topic）

`HMAC(NOSTR_SERVICE_KEY, "eventer/deck-sync/v1:" + deckId + ":" + version)` の hex。
世代ごとに替えるので、抜けた人が開いたままの画面は、新しい世代の宛先をそもそも購読していない。
宛先は絞り込みのための目印で、権限ではない。読めるかどうかは鍵で決まる。

### 4.4 抜けた人の画面（限界と対策）

- 抜けた瞬間に開いていた画面は、古い世代の鍵と宛先を持ったまま。ほかのメンバーが新しい世代に切り替わるまでは、送り合いが届く
- 対策: メンバーの画面は、受け取った差分の `v`（世代）が自分の世代より新しかったら、HTTP で `GET` を1回だけ取り直して新しい鍵に切り替える。また、差分の送信をやめる前に一度、取り直しも行う。
  抜けた人の `GET` は 403 になるので、その画面は同期を止めて「このスライドはもう編集できません」と出す（保存も 403 で止まるのは今と同じ）
- さらに、サーバーは鍵を作り直したときに、今の合図（kind 20078）で `deck-sync` という topic を送る。名前は topic の型に足す。開いている画面に「鍵が変わった」と知らせて、すぐ取り直させる。中身は `{rev}` だけ
- それでも、合図が届かないままの抜けた人の画面には、残りのメンバーが新しい世代に移るまでのあいだ届く。最悪でも、残りのメンバーが次の差分を受け取るか合図を受けて取り直すまで。これは仕様として受け入れ、docs に書く

## 5. 差分（op）のモデル

### 5.1 時計

各タブは `clientId`（タブごとの乱数 8 バイト）と、ハイブリッド論理時計 `hlc = { t: ms, c: counter }` を持つ。
比較の順番は `(t, c, clientId)`。この順番が、どのタブでも同じ全順序になる。

- 自分の操作: `t = max(now, last.t)`。同じ t なら `c+1`
- 受け取ったとき: `last = max(last, received)`（HLC の受信規則）。時計がずれたタブがあっても、あとから操作した側が勝つ順序は崩れない。
  ただし、未来に大きくずれた時計（> now+60s）の差分は捨てる（§8 の検証）

### 5.2 状態と「ぶつかったときの勝ち」

`DeckContent` の構造（slides[]・elements[]、要素は `deckElementSchema`）はそのまま。差分を当てる側だけが、次の「最後に書いた印」を持つ。

- 要素の欄ごと: `lww[slideId][elementId][field] = hlc`
- 要素の存在: `alive[slideId][elementId] = { hlc, alive: boolean }`（削除は印を残す。後から来た古い更新で生き返らせない）
- ページの存在と背景: `alive[slideId]`、`lww[slideId]["@slide"]["background"]`
- 並び: ページの並び、ページの中の要素の並び（重なり順）は、**分数の位置キー**（`pos: string`、fractional indexing）を持つ欄として扱う。
  並べ替えは `pos` 欄の上書き1つになる。表示は `pos` で並べ、同じ値なら id 順。これで並べ替えもふつうの「欄の上書き」になり、どの順に届いても同じ並びになる

`pos` は保存する中身には入れない（配列の順番がそのまま並びになる）。HTTP で受け取った中身に `pos` を振るときは、配列の順に機械的に振る。どのタブでも同じ値になる。

### 5.3 op の種類

```ts
type DeckOp =
  | { op: "slide.add", slideId, pos, background }                 // 生存の印＋欄
  | { op: "slide.remove", slideId }
  | { op: "el.add", slideId, element: DeckElement, pos }          // element は deckElementSchema で検証
  | { op: "el.remove", slideId, elementId }
  | { op: "el.set", slideId, elementId, fields: Partial<DeckElement & { pos: string }> }
  | { op: "slide.set", slideId, fields: { background?: string; pos?: string } }
  | { op: "title.set", title: string }
```

- 1回の送信（バッチ）は `{ v, clientId, hlc, ops: DeckOp[], baseRevision }`。`hlc` はバッチの最後の時計で、バッチ内の op は `(hlc, 並び順)` で順番付ける
- 当て方: それぞれの欄は、届いた印が手元の印より新しいときだけ上書きする。削除と生存も同じ印で比べる
- グループ（`groupId`）は要素の欄の1つとして扱う。まとめる・外すは、複数の要素への `el.set` になる
- 画像: アップロードは今までどおり HTTP（`PUT /api/decks/:id/images`）。返ってきた `src` を `el.set` で流す。画像の中身はリレーに載せない

### 5.4 文字

`text` は欄ごとの上書き。打っている人は 300ms ごとに `el.set {text}` を送る。同じ要素を2人で同時に打つと、あとから打った人の文になる。
文字 CRDT（Yjs など）は依存と保存形式が大きく変わるので入れない。発表スライドの文字は短い前提。
それでも、打っている欄が他人の更新で書き換わると打ちにくい。そこで、**自分がフォーカスしている文字欄には、他人の `text` を当てずに保留する**。保留したものは、フォーカスが外れたときに印を比べて当てる。

### 5.5 編集画面との関係（content を作る場所は1つ）

- 画面の `content`（`DeckEditorPage` の state）は「当てた結果」として作り直す。ローカルの操作は今までどおり `setContent` する。
  同期の層（`useDeckSync`）は、前の `content` と新しい `content` の差を `diffDeck(prev, next) → DeckOp[]` で取り出して送る。
  差を取るのは要素 id・ページ id 単位で、浅い比較で済む（要素は不変オブジェクトで作り直されているので、同一性で変わったかが分かる）
- ドラッグ中は `content` が変わらない（制約: docs/slide-editor.md §3）。なので、指を離した1回だけが差分になる
- 受け取った差分は `applyOps(content, meta, ops) → { content, meta }`（純関数。`lib/deckSync.ts`。React に依存しない）で当て、`setContent` する。
  このとき、**受け取った変更は履歴（Undo）に積まない**。`useEditorHistory` に `setContentFromRemote` を足し、`lastCommitted` も同時に進める。
  Undo で戻るのは自分の操作だけ。戻した結果は、ふつうの変更として差分になり、相手に送られる。
  相手がそのあと同じ欄を変えていれば、戻した側の時計が新しいので戻した値が勝つ。この挙動は docs に書く

### 5.6 収束の理由（短く）

- 全ての状態は「欄 → (値, 印)」の集まり。生存も並び（`pos`）も欄。印は全順序の HLC
- 当て方は「印が大きいほうを残す」だけなので、可換・結合的・冪等（同じものを2回当てても同じ）。どの順に届いても、同じ集合を受け取ったタブは同じ状態になる（LWW レジスタの集まり）
- 欄が欠けたまま要素が届くことはない。`el.add` は要素の全体を持ち、`el.set` が先に届いたときは、生存の印が無いので保留キュー（最大 500 op・30 秒）に入れ、`el.add` が来たら当てる。30 秒を過ぎた保留は捨てて、HTTP の取り直しを1回予約する

## 6. 送り方（クライアント）

### 6.1 接続

`ChatRelayPool`（`lib/nostrChat.ts`）を使う。タブごとに使い捨て鍵を作り、AUTH 応答もその鍵で行う。
`signalHub` と同じ考え方で、タブ全体で1つの接続を共有する。購読は `{kinds:[21078], "#t":[topic], since: now-120s}`。
`since` を付けるので、リレーが数分保持している古い分のうち、必要な直近分だけを受け取る。

### 6.2 kind

**21078** を使う。エフェメラル（20000–29999）の範囲で、20078（サーバー発の合図）とは用途を分けるために別の kind にする。
NIP の登録表で 21059（Ephemeral Gift Wrap）・22242・23194/5・24133・24242・27235・28934–6 と重ならないことを確かめた。
既存の 27888（鍵の所有証明）・9807（グループチャット）とも別。

### 6.3 イベントの形

| 項目 | 値 |
| --- | --- |
| kind | 21078 |
| pubkey | タブの使い捨て鍵（毎回同じタブでは同じ。差分の「誰が」は中身で示す） |
| tags | `["t", topic]`, `["v", version]`, `["-"]`（NIP-70。使い捨て鍵で AUTH して送る。§2 で受理を確認） |
| content | NIP-44 v2（鍵は `sync.key.secret`）で暗号化した JSON: `{ clientId, userId, name, hlc, baseRevision, ops }` または心拍 `{ clientId, userId, name, hlc, presence: { selected: string[], slideId, editingText?: elementId } }` |
| created_at | `floor(hlc.t / 1000)` |

`["-"]` を付けるのは、読めた人が別のリレーに持ち込むのを止めるため。中身は暗号文なので、漏れても読めない。ただ、ほかのチャットと同じ方針にそろえる。

### 6.4 間合い

- 差分は 150ms まとめて1件にする（ドラッグを離した・文字を打った、などが続くとき）。1件の暗号化前の大きさが 32KB を超えたら分ける
- 心拍は 2 秒ごと、ただし選択や編集中の欄が変わったらすぐ送る。タブが隠れているあいだは送らない。`pagehide` で「離れた」を1回送る
- 受け取った心拍は、6 秒届かなければ「編集中」から外す
- 送信は1タブあたり 1 秒に 10 件まで。超えたら、まとめる間隔を延ばす

## 7. 追いつき・取りこぼし・保存

- 開いたとき: HTTP の `GET` で中身と `revision` を受け取り、`pos` と印を初期化する。印はすべて `hlc0 = { t: deck.updatedAt, c: 0, clientId: "server" }`。
  そのあと購読を張る。リレーが返す直近分のうち、`hlc` が `hlc0` 以下のものは、保存済みの中身にすでに入っているので捨てる。新しいものは当てる
- 重複: `(clientId, hlc)` を受け取り済みの集合（直近 2,000 件）に入れ、2回目は捨てる。当て方そのものが冪等なので、集合はただの節約
- 取りこぼし（切断・スリープ）: 再接続して EOSE を受けたら、HTTP の `GET` を1回だけ取り直す（`signalHub` の配信画面と同じ考え方）。
  取り直した中身は、手元のまだ保存していない変更と合わせる必要がある。手元で印が `hlc0'`（取り直した時点）より新しい欄だけを、取り直した中身の上に当て直す
- 保存: 今の `useDeckSave`（800ms、1本ずつ、`baseRevision`）のまま、どのタブも保存する。中身はどのタブでも同じになるので、誰の保存も正しい。
  409 になったときに止めるのではなく、**取り直して当て直してから、新しい `revision` で保存し直す**（同期が生きているときだけ）。手元の未保存の欄は上の当て直しで残るので、失われない。
  同期が無い（`sync: null`・リレー未接続で 10 秒以上たった）ときは、今の 409 の案内のまま
- 保存の回数を減らす工夫: 受け取った差分だけで変わった中身は、自分からは保存しない。自分の操作があったタブだけが保存する。誰かが保存すれば、受け取った側の画面にも `revision` の前進が伝わる（心拍に `savedRevision` を載せる）。
  そのため、受け取った側が古い `baseRevision` で無駄な 409 を出すことはほぼ無い

## 8. 安全

- 鍵を持つのは、今のメンバーのタブだけ（`GET` が `deckEditableSql` を通るときだけ渡す）。鍵を持たない人は読めない。差分を当てても NIP-44 の認証付き暗号で弾かれる
- 鍵が漏れた場合（メンバーが外に貼るなど）、外の人がメンバーの画面に差分を送り込める。ただし、その差分が保存されるのは、誰かのタブが保存したときだけ。
  そして保存は、今までどおり HTTP でメンバー本人の権限で行う。被害は「メンバーの画面に変な変更が入り、気付かずに保存される」ところまで。メンバーを外せば鍵が替わる
- 当てる前に、全ての op を検証する:
  - `deckElementSchema` の上限（文字 10,000、ページ 300、ページあたり要素 200）を超える op は捨てる
  - 自分の世代と違う `v` は当てない。新しい世代なら取り直す（§4.4）
  - 未来に 60 秒以上ずれた `hlc` は捨てる
  - 1件の content が 64KB を超えるものは、復号せずに捨てる
- `userId`・`name` は中身にあるだけで、署名で保証されていない（同じ鍵を持つメンバーなら偽れる）。表示（「○○さんが編集中」）にだけ使い、権限には使わない。
  保存の「最後に保存: ○○さん」は、今までどおりサーバーが記録する
- リプレイ: 同じ差分を送り直されても、当て方が冪等なので状態は変わらない。昔の差分を送り直されても、印が古いので負ける

## 9. 個人のスライドにも使うか

既定は**チームのスライドだけ**。

- 個人のスライドで困るのは、同じ人が別のタブ・別の端末で開いたときだけ。今の 409 の案内で足りている
- 鍵の配布・作り直しの経路は、チームのメンバーの増減に結び付けて設計している。個人に広げても、作り直す契機が無いだけで、動作はする

オーナーが望めば、PR4 のあとに設定1つで広げられる（§12 Q1）。

## 10. 試験

- 単体（純関数・`lib/deckSync.ts`）:
  - 収束: ランダムな op 列を3つのタブに、異なる順番・重複・取りこぼしのあとの取り直しで当てる → 同じ中身になる（性質テスト、数百通り）
  - LWW の境界: 同じ欄・同じ `t` で `c` や clientId が違う／削除と更新が同時／並べ替えと削除が同時
  - `diffDeck` → `applyOps` で往復すると元に戻る
  - 文字欄のフォーカス保留
- サーバー: `GET` の `sync` はメンバーにだけ出る（運営・外の人・公開の閲覧には出ない）。メンバーが減る全ての経路で `version` が進む（経路を列挙して1つずつ）。`deck-sync` の合図が出る
- 画面: 2つのタブを模した結合テスト（同期の層を差し替え可能な送受信でつなぐ）。片方の操作がもう片方に出る。Undo は自分の操作だけ戻す。409 のときは取り直してから保存し直す
- 実地（必須）: ローカルの strfry を docker で立てる（本番と同じ版）。2つのブラウザを Playwright で別ユーザーとしてログインさせて、次を確かめる:
  - 同時に動かす、並べ替える、文字を打つ
  - 片方を切断して再接続する
  - 片方をチームから外す（世代が切り替わり、外れた側が止まる）
  - スマホ幅とPC幅で、「編集中」の表示を撮る
  - ステージングでは r / x を使う

## 12. オーナーに決めてほしいこと

- **Q1 個人のスライドにも効かせるか**: 既定は「チームのスライドだけ」（§9）。同じ人が PC とスマホで同時に開く使い方があるなら、広げる
- **Q2 抜けた人の画面**: 既定は「鍵を作り直して合図を送る。届くまでの短いあいだは、抜けた人の画面に差分が流れることがある」（§4.4）。これで足りるか。
  もっと厳しくするなら、作り直しのたびにメンバー全員の画面を強制的に読み直させる。そうすると編集中の人の手元が一瞬止まる
- **Q3 文字の同時編集**: 既定は欄ごとの上書きと、フォーカス中の保留（§5.4）。同じ文字の箱を2人で同時に打つ使い方が多いなら、文字 CRDT（Yjs 等）が要る。その場合は別の大きな設計になる
