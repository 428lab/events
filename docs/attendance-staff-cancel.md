# 運営による「キャンセル扱い」（無断欠席にしない）

- 状態: 実装（オーナー決定 2026-11-14）
- 関係: 参加実績の集計（`eventMembersRepo.participationStats`、#106）、参加解除（`changeMembership`）、
  Webhook（docs/webhooks.md）

## なぜ

当日、開始後に「行けなくなった」と連絡が来ることがある。本人がキャンセルしないままイベントが終わると、
出席チェックありのイベントでは**無断欠席**として数えられる（確定のまま・未チェックイン・終了済み）。
連絡があった人を無断欠席にしないため、運営がその人を「キャンセル扱い」にできるようにする。

## 決めたこと

- 運営（そのイベントのスタッフ）が、参加者一覧の「…」→「キャンセル扱いにする」で、確定している参加者を
  キャンセルにする。確認ダイアログを挟む。元には戻せない。
- **本人の取り消しと同じ扱い**（オーナー決定 A）。行は `canceled` で残り、`canceled_at` は操作した時刻。
  開始24時間以内（開始後・終了後を含む）なので、プロフィールの参加実績では**直前キャンセル**になり、無断欠席には数えない。
- 本人の参加解除と違い、**開始後・終了後でもできる**（連絡が開始後に来るため）。
  - 終了前: 本人の取り消しと同じく、個人 Entry と事前アンケートの回答を消し、先着枠のキャンセル待ちを繰り上げる。
  - 終了後: 繰り上げない（もう参加できない）。個人 Entry と回答は消さない（採点・表彰・回答の記録を残す）。
- 受付でチェックイン済み（出席）の人はできない（`409 already_attended`）。来ていた記録を書き換えない。
  確定していない人（申込中・キャンセル待ち・落選・スタッフ等）もできない（`409 not_confirmed_participant`）。
- 本人にアプリ内通知「運営があなたの参加をキャンセル扱いにしました」（種別 `info`。メール設定に従う）。
- 監査ログ `participation_cancel_by_staff`（実行した運営・対象・イベントID）。
- Webhook のキャンセル通知を送る。題名は「キャンセル（運営が記録）: イベント名」。

## API

`POST /api/events/:id/members/:userId/cancel`（`requireEventRole(["staff"])`）。
DB の書き込みは `changeMembership(..., { staffCancel: true, eventEnded })` に寄せる（本人の取り消しと同じ一括処理）。
一括処理の門で、操作者が運営であること・対象が確定の参加者で未チェックインであることを確かめる。
