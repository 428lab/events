# スタッフ向けの TODO リストとガントチャート（準備の段取り） (#393)

- 対象: `apps/server`（D1 スキーマ・新しいリポジトリ・新しいルート）、
  `packages/shared`（型・入力スキーマ・日付の扱い・文言）、`apps/web`（一覧とガント）
- 前提: #383（当日の裏方タイムライン）は**マージ済み**。本設計はその続きではなく**別軸**
- ステータス: **実装済み**（PR #397。完了 TODO の見せ方は #400 → PR #402 で調整）。
  見せ方 (8.) は相談のうえ P1 / G1 / D3 に決まった。実装で設計から変えた点は 11. にまとめた

---

## 1. なぜ作るか

準備の段取りを置く場所が無い。「会場を押さえる」「告知を出す」「備品を買う」は
イベント当日より**前**の仕事で、単位は日〜週。いまは運営の頭の中と外部のメモにある。

要件は6つ (#393)。

1. スタッフが TODO を足せる。**期限**を決められる
2. **個人に割り当てられる。** 未割り当てのものが分かる
3. 終わったら**閉じられる**
4. **ガントチャート**で期間と進み具合が見える
5. **依存関係**（A が終わらないと B に進めない）を持てる
6. **スタッフにしか見えない**

6 は #383 と同じ危険で、しかも今回は**性質が違う**。#383 は「参加者にも返す1本の
API に、参加者に見せない行が混ざる」形だったが、今回は**参加者向けの経路が1本も無い**
（新しい表・新しいルート・新しい画面）。漏れる可能性は #383 より小さいが、**小さいうちに
閉じておかないと「ついでにイベント詳細にも出そう」で開く**。3.5 でその閉じ方を決める。

4 と 5 は本質的に同じ機能である。ガントの価値の大半は「この帯が終わらないと次が
始まらない」が目で分かることにあり、依存が無いガントは日付付きの箇条書きと変わらない。

## 2. 調査結果

### 2.1 いまのデータの形（TODO に相当するものは無い）

`apps/server/migrations/` を 0001〜0072 まで見た。**準備の作業・タスクに相当する表は無い。**
近いものは3つあるが、どれも別物である。

| 表 | 何を持つか | なぜ今回に使えないか |
|---|---|---|
| `event_schedule_item` (#338/#383) | 当日のコマ。分単位・トラック・カーソル連鎖 | **時間軸が違う。** 日付だけの仕事を置くと `computeScheduleTimes` の連鎖に入る |
| `participation_slot` | 参加枠の定義 | 参加者の受け入れ枠であって作業ではない |
| `event_broadcast` (#172) | 一斉連絡の履歴 | 履歴。編集・完了・依存の概念が無い |

### 2.2 スタッフの判定（既にある。増やさない）

`apps/server/src/auth/roles.ts` に3つある。**用途が分かれていて、混ぜてはいけない。**

| 関数 | 通る人 | いまの用途 |
|---|---|---|
| `requireEventRole(["staff"])` | アプリ運営管理者 / `event_member.role='staff'` / コミュニティの owner・admin | タイムテーブル編集、イベント複製・削除 |
| `canManageEvent(eventId, user)` | 上とまったく同じ基準（ミドルウェアを通せない場面用） | #383 の「裏方が見える人」 |
| `isConfirmedEventStaff(eventId, userId)` | **そのイベントの `status='confirmed'` な staff だけ** | 一斉連絡 (#172)、イベント内モデレーション (#275) |

`canManageEvent` は「`requireEventRole(["staff"])` と同じ基準」と自分のコメントに書いてあり、
`requireEventRole` からも呼ばれている。**判定は実際に1本になっている。**

### 2.3 メンバーが外れるとき、何が起きるか（#380 と同じ観点）

`assignee` を持つ以上、ここを決めないと設計が成り立たない。**4通りある。**

| 起きること | 実装 | `user` 行 | `event_member` 行 |
|---|---|---|---|
| a. イベントから除名・自分で脱退 | `eventMembersRepo.remove` = `DELETE FROM event_member`（`eventMembers.ts:239`） | 残る | **消える** |
| b. staff → participant に降格 | `event_member.role` の UPDATE | 残る | 残る（role が変わる） |
| c. 退会申請 (#250) | `usersRepo.requestDeletion` = `user.deleted_at` を立てるだけ（`users.ts:661`） | **残る（deleted_at 付き）** | **残る** |
| d. 30日後の完全削除 (#244) | `DELETE FROM user`（FK が発火） | **消える** | CASCADE で消える |

**c が最も危ない。** 退会しても `event_member` の staff 行は残るので、
「`event_member` に staff 行があるか」だけで担当者を判定すると、
**退会した人の名前がスタッフの画面に出続ける**。#250 の目的
（他の利用者から見えなくなる）が果たされない。`usersRepo` には既に
`const ACTIVE = "deleted_at IS NULL"` があり、参照系はこれで除いている。
担当者の解決も**必ずこれを通す**（6.3）。

d は FK の設定次第。`notification.actor_id` (#380) と `venue_photo.user_id` (0032) は
`ON DELETE SET NULL`、`event_broadcast.created_by` (0062) は `ON DELETE CASCADE`。
**今回は `SET NULL`**（4.1 で理由を書く）。

### 2.4 アカウント統合で付け替えが要る（#380 6.2 と同じ罠）

`users.ts` の `mergeUsers` に「UNIQUE の無い参照列は単純に付け替え」の `simple`
リストがある。**ここに足し忘れると、負け側の `user` 行を消した瞬間に
`ON DELETE SET NULL` が発火し、統合したはずの担当が黙って未割り当てになる**
（#380 が `notification.actor_id` の行に同じ注意書きを残している）。

### 2.5 イベントの複製は何をコピーしているか

`apps/server/src/routes/events.ts:401` の `POST /:id/duplicate`。
コピーするのは基本情報・参加枠の定義・採点基準・表彰の定義・イベント画像。
コピーしないのは参加者・投票・受賞結果・**タイムテーブル**、そして
**募集締切 (`registrationDeadline`) と抽選日時 (`drawAt`)**。

締切と抽選日時をあえてコピーしない理由がコメントに書いてある。

> 締切は複製元の開催日に紐づいた絶対時刻で、複製では開催日時を 0 に戻している。
> そのまま持ち越すと「作った瞬間もう締め切られている」下書きができてしまう。

**これは本設計の TODO の日付にそのまま当てはまる**（7. で使う）。

### 2.6 参加者に届く経路（TODO が混ざりうる場所の洗い出し）

いま参加者・外部にイベントの中身を配っているのは6経路ある。
イベント詳細 `GET /events/:id`、タイムテーブル `GET /events/:id/timetable`、
前日リマインダーのメール（`lib/email.ts`）、出席 CSV（`routes/attendanceCsv.ts`）、
フィード（`routes/feeds.ts`）、公開ページ・公開プロフィール（`routes/public.ts`）。
これに `notification` 表を加えた7か所に、**本設計は TODO を1件も出さない**。
「出さない」ことは 9.1・9.2 で機械が守る（通知を出さない理由は 10.）。

## 3. 決めたこと（結論）

1. **新しい表を2つ作る**（`event_todo` と `event_todo_dep`）。
   `event_schedule_item` には**載せない**（3.1）
2. **日付は「日」だけ持つ。時刻を持たない。** 形式は `TEXT 'YYYY-MM-DD'`（3.2）
3. **依存関係は1種類だけ**（「先が終わってから後を始める」）。
   開始・終了の組み合わせもラグも作らない（3.3）
4. **循環は書き込みの時点で作らせない。**
   ただし**読み側は循環データでも必ず終わる**ように書く（3.4）
5. **表は1つのリポジトリに閉じ込め、参加者向けの経路を1本も作らない。**
   閉じていることを SQL 監査テストで守る（3.5）
6. **テンプレートは作らない**（#364 待ち）。代わりに**イベントの複製で TODO をコピーする**（7.）
7. **#383 とはデータで繋がない。** 画面の行き来（リンク）だけ置く（3.6）
8. 状態は `open` / `done` の2値。**「待ち」も「遅れ」も保存せず、必ず導出する**（3.7）

### 3.1 新しい表にする（`event_schedule_item` に載せない）

3案を比べた。

#### 案A — `event_schedule_item` に `kind` 列を足して同居させる（採らない）

- **代償1（致命的）**: #383 が身をもって示したとおり、既存の絞り込みが
  `placement != 'unassigned'` のような**拒否リスト**で書かれていると、新しい値は
  **黙って通り抜ける**。`event_schedule_item` を読む SQL は #383 の調査で
  **13 経路**あった。1つ足すたびに 13 か所を確かめ直すことになる
- **代償2**: 列の意味が合わない。TODO には `starts_at`（epoch ms）も `duration_min` も
  `placement` も `trackIds` も無く、逆に schedule item には `due_on` も `status` も
  `assignee` も無い。**両方が半分ずつ NULL の表**になる
- **代償3**: `computeScheduleTimes` のカーソル連鎖に入る。#383 は「裏方はカーソルを
  進めない」の1行を足すのに1節ぶんの検討を要した。日付しか持たない行が混ざると
  その規則がもう1種類増える

#### 案B — 新しい表を2つ作る（**採用**）

参加者向けの読み手が**ゼロ**から始まる。#383 が「13 経路のうち5か所に条件が書かれて
いなかった」状態から始めざるを得なかったのに対し、こちらは**閉じた状態を最初から作れる**。
閉じ続けることだけを守ればよい (3.5)。依存関係は多対多なので、どのみち2本目の表が要る
（schedule item に同居させても `event_todo_dep` 相当は必要で、**同居の利点が消える**）。
代償は表が2つ増え、複製・削除・統合で見る場所が増えること
→ 削除は `ON DELETE CASCADE` で自動、複製は 7.、統合は 2.4 で1行ずつ潰す。

#### 案C — #384（役割タグ）と共有する汎用の `task` 表（採らない）

**#384 は別軸**だと issue が明言している（あちらは当日の持ち場、こちらは準備の仕事）。
共有した瞬間に「この行は準備の仕事か当日の持ち場か」を区別する列が要り、案A と同じ形になる。
#384 はまだ設計されていない。**存在しない要件に合わせて表を作らない。**

### 3.2 日付は「日」だけ持つ。`TEXT 'YYYY-MM-DD'`

準備は日〜週の単位で立てる。「9/1 までに会場を押さえる」であって
「9/1 14:30 までに」ではない。**時刻を持たせると、持たせた時刻が意味を持ってしまう。**

保存形式を3つ比べた。

| 形式 | 利点 | 代償 |
|---|---|---|
| `INTEGER` epoch ms | 既存のイベント日時と同じ | **タイムゾーンで日がずれる。** UTC 0時で保存した 9/1 を `formatMonthDay`（ローカル）で描くと、UTC-5 の人には 8/31 と出る |
| `INTEGER` `20260901` | ずれない・比較できる | 日の加減算に専用の関数が要る。DB を直接見たとき読めるが、`<input type="date">` との間で毎回変換が要る |
| **`TEXT 'YYYY-MM-DD'`（採用）** | ずれない。SQLite の TEXT 比較が**そのまま日付順**。`<input type="date">` の `value` と**まったく同じ形**なので画面の端で変換が要らない | 加減算に関数が要る（ガントの列計算で使う。`packages/shared` に1つ置く） |

**「誰のカレンダーの日か」は決めない。** 9/1 は誰にとっても 9/1 として表示・入力される。
イベントにタイムゾーン列は無く、足すのは範囲外。瞬間として持つ案は
**同じ仕事の期限が人によって別の日に見える**ことを意味し、段取りを揃える道具として壊れている。
形は `CHECK` + `GLOB` でも守る（4.1）。

### 3.3 依存関係は1種類だけ

`event_todo_dep(todo_id, depends_on_id)` の意味を**1つに固定する**。

> `todo_id` の仕事は、`depends_on_id` の仕事が `done` になるまで着手できない。

一般のガントには4種類（FS / SS / FF / SF）とラグがある。**採らない。**
issue も「最初は1種類で足りるはず」と書いている。
4種類あると帯を見た人が**どの種類の線なのかを線から読めず**、入力する側は毎回選ばされる。
「待ち」の判定も種類ごとに変わる。1種類なら「先が `done` でなければ待ち」の
**1つの述語**で済み、保存せず導出できる（3.7）。
ラグ（「3日空けて」）は後続の `starts_on` を3日後に置けば表現できる。
**同じことを2通りで書けるようにしない。**

**多対多にする。** 「告知を出す」は「会場を押さえる」と「登壇者を決める」の**両方**を待つ。
`event_todo.depends_on_id` を1本の列にすると、この普通の形が偽の直列に潰れる。
表が1つ増える代償は、概念が増えないので小さい。

### 3.4 循環は作らせない。ただし読み側は循環でも終わる

**書き込みで弾く**（`400 todo_dep_cycle`）。循環があると「待ち」の述語が意味を失い
（A も B も永久に待ち）、ガントの行順も定義できない。**壊れた状態を作れてしまうと、
読み手全員が壊れた状態の見せ方を持つことになる**（門の上に門）。
判定は `A → B` を足すとき「**B から A へ既に到達できるか**」の1問で、
自己参照 (`A → A`) も同じ判定で落ちる。イベント1つぶんの辺を全部読んで JS で BFS する
（件数と依存本数に上限を置くので計算量が押さえられる。`WITH RECURSIVE` で書く案もあるが、
終了条件を SQL で正しく書くより JS のほうが読めてテストしやすい）。

**それとは別に、読み側の走査を有限にする**（訪問済み集合＋深さ上限）。
これは「門の上に門」ではない。**入口の判定は「正しい入力か」の話、
走査の有限性は「どんな入力でも終わるか」というアルゴリズム自身の性質**で、別の問いである。
一括投入・複製・将来の別経路が検査を通さずに辺を作りうる以上、読み側が無限ループする
可能性を残してはいけない（その先にあるのはスタッフ全員の画面が固まることである）。
循環を含む項目には印を出し、**壊れていることを黙って隠さない**。

### 3.5 表を1つのリポジトリに閉じ込める

#383 は「絞り込みは1か所」と書いてあるのに実際は4か所（＋書かれていない4か所）
だった、というところから始めなければならなかった。**今回は0か所から始められる。**
したがって `audience` 引数（#383 5.1）に相当するものは**作らない**。代わりに不変条件を1つ置く。

> **`event_todo` / `event_todo_dep` を読み書きする SQL は
> `db/repositories/eventTodos.ts` の中にしか無い。**

`audience` を必須引数にする形は「1本の API が2つの聞き手を持つ」ときの解であって、
聞き手が1種類しかないここで真似ると、**存在しない参加者向け経路のために引数を配り歩く**
ことになる。守るべき性質が違うので守り方も変える。
不変条件は 9.2 の監査テストで機械が守る（#383 9.10 と同じ発想・同じ実装）。

### 3.6 #383 とはデータで繋がない（画面の行き来だけ置く）

issue は「準備の最後が当日の最初につながるので、まったく無関係にはできない」と書いている。
**それでも v1 では列で繋がない。** `event_todo.schedule_item_id` を先回りして足さない。

- 繋ぐと、必ず「TODO を `done` にしたら当日のコマも済んだことになるのか」
  「コマの時刻を動かしたら期限も動くのか」の2問が生まれる。
  **時間モデルが違う2つの表を双方向に同期する**のは、この機能が腐る場所そのもの
- #384 が `event_schedule_item` に役割と必要人数を載せる予定である。
  TODO の担当がそこに繋がると、issue が「混ぜるな」と書いた2つの軸が繋がってしまう
- 実際の必要は**リンクで足りる**。TODO の画面と当日のタイムライン (#383) に
  互いへのリンクを1本ずつ置く。スキーマ0行、ずれる余地0

**代わりに、どちらに書くかの線引きを文言で示す**（両方の画面の空状態の案内に書く。
書かないと同じ仕事が両方に溜まる）。
日付だけで当日より前の仕事 → **TODO**。時刻があり当日の段取り → **タイムライン (#383)**。

### 3.7 「待ち」も「遅れ」も保存しない

**待ち**（着手できない）= `status='open'` かつ依存先に `done` でないものがある。
**遅れ** = `status='open'` かつ `due_on < 今日`。

どちらも列にしない。列にすると、依存先を `done` にした瞬間・日付が変わった瞬間に
**更新して回る仕事**が生まれ、更新漏れが「実際は動けるのに待ちと表示される」形で残る。
導出なら古くならない。

**遅れの判定は画面側で、見ている人の「今日」で行う。** サーバーで判定すると
サーバーの時計とタイムゾーンを1つ決めることになり、3.2 の決定と矛盾する。
判定は `apps/web` に1か所（`lib/todoGantt.ts` の純関数）だけ置く。

進捗率（0〜100%）は**持たない**。自己申告の百分率は常に間違っていて、しかも間違って
いることが分からない。細かくしたければ TODO を分ければよい。「進み具合」は
`done` / 遅れ / 待ちの件数で見せる（8.）。

## 4. マイグレーション

### 4.1 `apps/server/migrations/0073_event_todo.sql`

```sql
-- スタッフ向けの TODO とガントチャート (#393)。
--
-- 準備期間（日〜週）の段取りを置く。「会場を押さえる」「告知を出す」「備品を買う」
-- のような、イベント当日より**前**の仕事。
--
-- **当日の段取り (#383) とは別の表にしている。** あちらは event_schedule_item で
-- 分単位・トラック・カーソル連鎖を持つ。同じ表に載せると
--   - 参加者向けの絞り込みが 13 経路あり、値を1つ増やすたびに全部を確かめ直すことになる
--     （#383 で、拒否リスト形式の絞り込みを新しい値が黙って通り抜けることが実証済み）
--   - epoch の starts_at / duration_min / placement と、due_on / status / assignee が
--     互いに半分ずつ NULL の表になる
--   - computeScheduleTimes の連鎖の規則がもう1種類増える
-- 時間軸が違うものを同じ表に載せない。
--
-- **この2つの表は参加者に1行も返さない。** 読み書きする SQL は
-- db/repositories/eventTodos.ts の中にしか置かないこと。この不変条件は
-- test/staff-todo-sql-audit.test.ts が機械で守る（#383 の SQL 監査と同じ仕掛け）。
-- 「イベント詳細にも出そう」と思ったら、まずそのテストの許可リストに理由を書く。

CREATE TABLE event_todo (
  id TEXT PRIMARY KEY,
  event_id TEXT NOT NULL REFERENCES event(id) ON DELETE CASCADE,

  title TEXT NOT NULL,
  -- 補足。任意。長文の手順書ではなく「どこに電話するか」程度を想定
  note TEXT,

  -- 期間。**日付だけ**を持ち、時刻は持たない (#393 の対象は日〜週)。
  --
  -- 形式は 'YYYY-MM-DD' の TEXT。
  --   - epoch ms にすると、UTC 0時で保存した 9/1 が
  --     ローカル整形で 8/31 に見える人が出る（同じ期限が人によって別の日になる）
  --   - TEXT の辞書順が**そのまま日付順**なので ORDER BY / 比較がそのまま効く
  --   - <input type="date"> の value と同じ形なので、画面の端で変換が要らない
  -- どのタイムゾーンの日かは決めない。9/1 は誰にとっても 9/1 と表示・入力される。
  --
  -- 両方 NULL でよい（日付未定の仕事は一覧にだけ載り、ガントには出ない）。
  -- starts_on だけ NULL のときは due_on の1日だけの帯（マイルストーン）として描く。
  starts_on TEXT CHECK (starts_on IS NULL OR starts_on GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  due_on    TEXT CHECK (due_on    IS NULL OR due_on    GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),

  -- 2値だけ。'blocked'（待ち）と 'overdue'（遅れ）は**列にしない**。
  -- どちらも依存先の状態と今日から導出できる。列にすると、依存先を done にした
  -- 瞬間・日付が変わった瞬間に更新して回る仕事が生まれ、漏れると
  -- 「実際は動けるのに待ちと表示される」形で古びる。導出は古びない。
  status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'done')),
  done_at INTEGER,

  -- 担当（1人）。**複数人・人数・役割は #384 の仕事**なので、ここでは増やさない。
  --
  -- ON DELETE SET NULL:
  --   完全削除 (#244) でユーザー行が消えたときに、仕事そのものを消したくない。
  --   「会場を押さえる」はイベントの仕事であって担当者の持ち物ではない。
  --   CASCADE にすると、スタッフが1人アカウントを消しただけで
  --   その人が担当していた準備が全部消える。notification.actor_id (#380) と
  --   venue_photo.user_id (0032) と同じ形。
  --
  -- **除名・降格・退会申請では、この列は触らない。** どれも user 行も
  -- event_member 行も残る／片方だけ消える（設計 2.3 の表）ので FK は発火しない。
  -- 「まだ担当者か」は取得時に event_member と user.deleted_at を見て導出する。
  -- ここを消して回ると、メンバーを外す経路（除名・脱退・降格・退会）の数だけ
  -- 同じ契約が散る。導出なら1か所で済む。
  assignee_user_id TEXT REFERENCES user(id) ON DELETE SET NULL,

  -- 誰が足した仕事か。表示には使わず、荒れたときに辿るためだけに持つ。
  -- 担当と同じ理由で SET NULL（作成者が消えても仕事は残す）
  created_by TEXT REFERENCES user(id) ON DELETE SET NULL,

  -- 一覧の並び。**ガントの行順もこれに従う**（日付順や依存の順に自動で並べ替えない。
  -- 並べ替えると、依存を1本足しただけで行が動き、一覧とガントで順序が食い違う）
  sort_order INTEGER NOT NULL,

  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,

  -- 逆さまの期間を作らせない。DB で表現できる不整合は DB で止める。
  -- **表単位の制約なので、列の定義を全部書き終えてから置く。**
  -- SQLite は列定義より前に表単位の制約が来ると、そこから先の列を
  -- 構文エラーにする（starts_on の直後に置いた最初の版がそれで通らなかった）
  CHECK (starts_on IS NULL OR due_on IS NULL OR starts_on <= due_on)
);

-- 一覧はイベント単位で全件引く（件数に上限を置くので、ページングはしない）。
CREATE INDEX idx_event_todo_event ON event_todo(event_id, sort_order);

-- 依存関係。**1種類だけ**: todo_id は depends_on_id が done になるまで着手できない。
--
-- 開始・終了の組み合わせ（SS / FF / SF）とラグは作らない。
--   - 種類が増えると、帯の間の線を見た人が「どの種類か」を線から読めない
--   - 「待ち」の判定が種類ごとに変わる。1種類なら述語は1つで済み、保存せず導出できる
--   - ラグ（3日空ける）は後続の starts_on を3日後に置けば表現できる。
--     同じことを2通りで書けるようにしない
--
-- 多対多にしているのは、「告知を出す」が「会場を押さえる」と「登壇者を決める」の
-- **両方**を待つのが普通だから。event_todo に depends_on_id を1列足す案だと、
-- この普通の形が偽の直列に潰れる。
--
-- 循環 (A→B→A) は**サーバーが書かせない**（辺を足すとき、逆向きの到達可能性を
-- BFS で見て弾く）。DB の制約では表現できない。
-- ただし読み側の走査は、万一循環が入っても必ず終わるように書くこと
-- （入口の検査は「正しい入力か」、走査の有限性は「どんな入力でも終わるか」で、別の話）。
CREATE TABLE event_todo_dep (
  -- 待つ側（後）
  todo_id       TEXT NOT NULL REFERENCES event_todo(id) ON DELETE CASCADE,
  -- 待たれる側（先）
  depends_on_id TEXT NOT NULL REFERENCES event_todo(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  -- 同じ辺を二重に持たせない
  PRIMARY KEY (todo_id, depends_on_id)
);

-- 「この仕事を待っているのは誰か」を引く向き（PRIMARY KEY は逆向きだけを賄う）。
-- 循環判定の BFS と、ガントの線を引くのに両向きが要る
CREATE INDEX idx_event_todo_dep_reverse ON event_todo_dep(depends_on_id);
```

**埋め戻しは無い。** 新しい表で、既存データに触れない。

## 6. API

新しいサブアプリ `apps/server/src/routes/eventTodos.ts`。
`worker.ts` で `api.route("/events", eventTodoRoutes)`。

### 6.1 権限（`requireEventRole(["staff"])` を使う。`isConfirmedEventStaff` にしない）

```ts
export const eventTodoRoutes = new Hono<AppEnv>();
eventTodoRoutes.use("*", requireAuth);
// 一覧・作成（/:id/todos）と、その配下すべてに同じ権限をかける（eventBroadcast.ts と同じ形）
eventTodoRoutes.use("/:id/todos", requireEventRole(["staff"]));
eventTodoRoutes.use("/:id/todos/*", requireEventRole(["staff"]));
```

`isConfirmedEventStaff`（一斉連絡・モデレーションが使う、より狭い判定）にしないのは、
**#383 の「裏方が見える人」と同じ基準にそろえるため**。あちらは `canManageEvent`
（＝`requireEventRole(["staff"])` と同じ基準）で「編集できる人」「裏方が見える人」
「`PUT` が通る人」を1本にした。準備の段取りは当日の裏方と**同じ運営情報**なので、
見える範囲が2種類あると「タイムラインは見えるのに TODO は見えない人」が生まれ、
どちらが正かを説明できない。`isConfirmedEventStaff` が狭いのは一斉連絡が
**取り消せず全員に届く**操作だから (#172 のコメント)で、TODO の編集は取り消せる。

**代償を1つ明記する。** コミュニティの owner/admin とアプリ運営管理者は
`event_member` 行を持たないことがある。**その人たちは見えるが、担当には指定できない**
（6.3 の条件を満たさないため）。意図した非対称で、
「担当は、そのイベントのスタッフとして名前が並んでいる人だけ」を優先した。

### 6.2 エンドポイント

| メソッド・パス | 中身 |
|---|---|
| `GET /api/events/:id/todos` | 一覧（下記） |
| `POST /api/events/:id/todos` | 追加。`{ title, note?, startsOn?, dueOn?, assigneeUserId? }` |
| `PATCH /api/events/:id/todos/:todoId` | 更新。上記＋`status`。**送ったキーだけ変える**（6.4） |
| `DELETE /api/events/:id/todos/:todoId` | 削除。依存の辺は CASCADE で消える |
| `PUT /api/events/:id/todos/order` | 並べ替え。`{ ids: string[] }`（そのイベントの全 id） |
| `POST /api/events/:id/todos/:todoId/deps` | 依存を足す。`{ dependsOnId }` |
| `DELETE /api/events/:id/todos/:todoId/deps/:dependsOnId` | 依存を外す |

**タイムテーブル (#340) のような「全件を送って差分保存＋版番号」にしない。**
あちらが差分保存なのは、表計算のような編集画面を持つから。
TODO は「チェックを付ける」「日付を1つ直す」の単発操作が主で、
版番号・編集ロック・409 の仕組みを持ち込むと、
**ボタン1つ押すのに全件を送り返す**ことになる。同時編集は項目ごとの後勝ちでよい
（違う項目を触っている限り衝突しない）。

### 6.3 `GET /api/events/:id/todos` のレスポンス

```ts
export interface EventTodosPayload {
  todos: EventTodo[];
  /** 依存の辺。項目の中に入れず平らに返す。ガントの線も待ちの判定も
   * 全体のグラフが要るので、項目ごとに切って持たせる意味がない */
  deps: Array<{ todoId: string; dependsOnId: string }>;
  /** 担当に指定できる人（＝このイベントの confirmed な staff、退会者を除く）。
   * 画面の選択肢に使う。**todos の中の assignee とは別物**で、
   * 担当を外れた人はここに居ない */
  assignable: TodoAssignee[];
}

export interface EventTodo {
  id: string;
  title: string;
  note: string | null;
  startsOn: string | null;   // 'YYYY-MM-DD'
  dueOn: string | null;
  status: "open" | "done";
  doneAt: number | null;
  /** 担当の状態。**3値で返す**（4.1 のとおり列は持たず、ここで導出する）
   *  - "unassigned" … 誰も割り当てていない（要件2の「未割り当て」）
   *  - "active"     … いまもこのイベントの confirmed な staff で、退会していない
   *  - "left"       … 担当は入っているが、上を満たさない
   *                   （除名・脱退・staff から降格・退会申請中） */
  assigneeState: "unassigned" | "active" | "left";
  /** "active" のときだけ入る。**"left" では必ず null**（下の注） */
  assignee: TodoAssignee | null;
  sortOrder: number;
}
```

**`"left"` で名前を返さない理由。** `"left"` には
「除名された」「降格した」「退会申請した (#250)」が混ざる。
このうち**退会は「他の利用者から見えなくなる」ことが目的**なので、名前を出せない。
3つを区別して出し分ける案もあるが、**区別する状態が増え、1つ間違えると
退会者の名前が出る**。1つの規則（担当として有効でないなら名前は出さない）にして、
画面は「担当者が外れています（要再割り当て）」と出す。
失うのは「誰が担当だったか」の便宜だけ。

**完全削除 (#244) の後は `assignee_user_id` が NULL になる**（FK の `SET NULL`）ので
`"unassigned"` に落ちる。`"left"` と区別が付かないが、これは正しい（痕跡を残さない）。

`assignable` の SQL は `event_member.role='staff' AND event_member.status='confirmed'`
かつ `user.deleted_at IS NULL`。**`deleted_at` を落とすと退会者が選択肢に並ぶ**（2.3 の c）。

### 6.4 入力の扱い（#383 4.2 の教訓）

**省略されたキーは「いまの値を保つ」。既定値を埋めない。**
`PATCH` のスキーマは全キー `.optional()` にする。

#383 は `visibility` に `.default("public")` を書いたせいで
「その列を知らない古いクライアントの保存が、裏方を全件公開に戻す」穴を作りかけた。
本設計は `PATCH` が部分更新なので構造的に同じ穴は空かないが、
**既定値を埋める書き方をしない**という規則自体はそろえる。

`startsOn` / `dueOn` / `assigneeUserId` は **NULL を明示できる**必要がある
（担当を外す・日付を消す）ので、`z.string().nullable().optional()` にして
「キーが無い＝保つ / `null`＝消す」を区別する。この区別は
**スキーマのコメントに書く**（読んだ人が `undefined` と `null` を取り違えると、
チェックを外したつもりで担当が消える）。

### 6.5 エラー

| コード | いつ |
|---|---|
| `todo_limit` | `EVENT_TODO_LIMIT` を超える追加 |
| `todo_dep_limit` | `TODO_DEPS_PER_ITEM` を超える依存 |
| `todo_dep_self` | 自分自身への依存 |

確かめないと、別イベントの id を指す辺が作れ、依存グラフがイベントをまたぐ。
子リソースの所有チェックは、このプロジェクトのセキュリティ点検で
「必須」と決まっている項目でもある。

## 7. イベントの複製（TODO はコピーする。日付と担当はコピーしない）

**コピーする。** これは 3. の 6 番目の決定「テンプレートを作らない」の**代わり**である。

- コピーする: `title` / `note` / 依存の辺 / `sort_order`
- コピーしない: `starts_on` / `due_on` / `assignee_user_id` / `status` / `done_at`
  （新しい行はすべて `open`・日付なし・未割り当て）

### 7.1 なぜテンプレートではなく複製か

**テンプレートは範囲外にする。** 理由は3つ。(1) **#364（保存データの言語）が未決**で、
既定テンプレを日本語で保存しても訳を引く形にしても #364 の結論を先取りする。
(2) 既定を日本語で保存すれば、#364 が「これはバグだ」と言っているものを自分から増やす。
(3) テンプレートには**持ち主**という2本目の未決の軸がある（サービス共通 / コミュニティごと /
イベントごと）。#384 も同じ判断で止まっている。

**複製なら、どちらの問いにも答えずに「毎回同じ準備」の価値が出る。** コピーされる文言は
主催者が自分で打った文言なので言語の決めごとが要らず、持ち主の問いも起きない
（複製元のイベントが持ち主）。テンプレートが本当に要るなら、#364 決着後に
「よく複製されている TODO の集合」という実データを見てから設計できる。

### 7.2 なぜ日付をコピーしないか

`POST /:id/duplicate` は開催日時を 0（未定）に戻す。既存コードは同じ理由で
募集締切と抽選日時をコピーしていない（2.5）。TODO の期限も同じ絶対日付で、持ち越すと
**作った瞬間に全部が「遅れ」になった段取り**ができる。

「開催日からの相対日数として持ち越す」案（例: 開催14日前）も採らない。日付の持ち方が
**絶対と相対の2通り**になり、さらに複製の時点では新しい開催日が決まっていないので
「開催日が決まったら TODO をずらす」処理が要る。イベントの日付更新にぶら下がる隠れた
副作用は、この機能でいちばん作りたくないもの。要るかは複製が使われてから分かる（10.）。

依存の辺はコピーする。**手で打ち直すといちばん面倒な部分**で、日付と違って複製先でも
意味が変わらない。

### 7.3 実装

`routes/events.ts` の複製ハンドラの末尾（表彰の定義のコピーの後）に
`await eventTodosRepo.copyForDuplicate(src.id, created.id, user.id)` を1行足す。
辺の張り替え（旧 id → 新 id の対応表）は**リポジトリの中に閉じる**
（3.5 の不変条件を破らない）。

  行の高さを2つの器で厳密にそろえる必要があり、狭い画面で破綻する

### 8.3 ガントの描き方（**外部ライブラリを足さない**）

`TimetableGrid.tsx` / `timetableLayout.ts` (#338) の型をそのまま使う。

- 純関数の layout（`lib/todoGantt.ts`）と描画（`components/TodoGantt.tsx`）に分ける。
  **layout は DOM を測らない。** 列幅と行高を定数にすれば、帯の位置も線の座標も
  入力だけから決まる。だから `ResizeObserver` も ref も要らない
- CSS Grid（`gridTemplateColumns: 見出し列 + repeat(日数, 列幅)`）。帯は
  `gridColumn` / `gridRow` を inline style で当てる（`sx` に入れるとクラスが帯の数だけ
  増える、と `TimetableGrid` のコメントが書いている）。見出し列は sticky。
  横スクロールは外側の `role="region"` + `tabIndex={0}` が持つ
- **描く幅を区切る。** `timetableLayout.ts` が「手入力の任意 epoch なので、年を
  打ち間違えた1件で行数が数百万になり画面が固まる」と書いて7日窓を入れているのと
  同じ問題が日付でも起きる。**「最も多くの項目が収まる
  `TODO_GANTT_WINDOW_DAYS`(=120) 日間」**を描き、外れた項目は一覧に落とす（消さない）。
  「最も早い項目を基準」にしないのも同じ理由（過去側の打ち間違い1件で全部外れる）
  - **日付を持つ項目のすべてが窓より長いときのフォールバック**（実装後の
    レビューで発覚。150日のスポンサー募集1件だけ、のような普通の入力で
    「窓に丸ごと収まる項目」が0件になり、素朴に書くとページごと描けなくなる）:
    最も早い開始日に窓を置き、**帯を窓の端で切って描く**。「一覧へ落とす」
    だけにしないのは、唯一の項目が長いだけでガントが空になるため。
    切った項目は `clippedIds` で返し、画面が「帯は途中まで」と注記する
    （帯の長さ＝期間だと読まれるので、黙って短く見せない）。
    窓に1日も触れない項目は従来どおり一覧へ落とす
- 列幅は窓の広さから決める（`dayColPx(span)`）。短い窓なら日付を書いた広い列、
  長い窓なら細い列＋週・月の目盛りだけ。**規則が2つになるわけではない**
- 今日の縦線、土日の薄い網掛け、`done` は塗りつぶし＋取り消し線、遅れは左端に赤、
  待ちは薄い塗り＋鍵アイコン（#383 が裏方に使ったのと同じ記号）

**依存の線の描き方:**

- 案D1 … 線を描かず、帯と一覧の行にチップ（「⟵ 会場を押さえる」）だけ出す。
  狭い画面でも読めるが、繋がりを目で追えない
- 案D2 … SVG のオーバーレイで常時 L 字の線を引く（座標は layout が計算するので
  DOM 計測は不要）。狭い画面では線が絡まる。線の経路探索はしない
- **案D3（採用） … 既定は案D1、選んだ項目の依存だけ線で強調する。**
  案D2 に選択状態を足すだけで線の絡まりが実用上消える

### 8.4 フィルタと集計

上部にチップを並べる。**すべて同じ1本の一覧から画面側で絞る**
（サーバーに絞り込みの口を増やさない。増やすと 3.5 の「閉じた1本」が崩れる）。
「自分の TODO」「未割り当て」（要件2）、「担当者が外れた」（`assigneeState === "left"`）、
「遅れ」（3.7 の導出。**完了したものは遅れに数えない**）、「完了を含める」（既定は `open` だけ）。
集計は「未完了 N / 遅れ N / 待ち N / 完了 N」で、これが要件4の「進み具合」にあたる。

**「自分の TODO」を横断（全イベント）で見る画面は作らない。**
作ると `event_todo` を読む2本目の経路ができ、そこで「そのイベントのスタッフか」を
**イベントごとに**判定し直すことになる。3.5 の不変条件がいちばん壊れやすい形。
要るなら別 issue で、その判定の置き場から設計する（10.）。

### 8.6 文言

`packages/shared/src/i18n/messages/staffOps.ts` に足す（`ja` / `en`）。
スタッフ専用画面の文言はこのファイルが持つ、と自身のコメントに書いてある。
**実装上の語（`assigneeState` / `dep` / `blocked`）を利用者向けの文言に出さない。**
「待ち」「担当者が外れています」「先に終わらせる仕事」のように振る舞いで書く。

## 9. テストが守っていること

`apps/server/test/staff-todo.test.ts` と `staff-todo-sql-audit.test.ts`。
web は `apps/web/src/lib/todoGantt.test.ts` と表示のテスト。

### 9.1 参加者に漏れない（最重要）

- `participant` / `judge` / `observer` / 非メンバーの `GET /:id/todos` → 403、未ログイン → 401、
  `staff` → 200 で全件（絞りすぎていないことの確認）。**役割ごとに1本ずつ。まとめない**
- **書き込み6本すべて**（`POST` / `PATCH` / `DELETE` / `PUT order` / dep の追加・削除）で
  `participant` が 403。1本にまとめない（#383 で「4か所のうち1か所だけ直っていた」事故が
  実際に起きている）
- 参加者向けの既存6経路（2.6）に **TODO の題名の文字列が現れない**ことを1本ずつ。
  id ではなく題名で照合する（id だけだと「id は返すが中身は伏せる」形にしたとき通る）

### 9.2 SQL 監査（`staff-todo-sql-audit.test.ts`）

`apps/server/src/` を読み、`event_todo` / `event_todo_dep` を含む SQL が
`db/repositories/eventTodos.ts` 以外に1つも無いことを確かめる。例外は許可リストに
理由つきで明示する。#383 の監査と同じ形で、切り出しは `test/lib/sqlScan.ts` を共有。
本設計の不変条件 (3.5) は**コメントでは守れない**ので機械に守らせる。

### 9.3 循環

自己依存 → `todo_dep_self`、逆辺 → `todo_dep_cycle`、**推移的な循環**（`A→B→C` に `C→A`）も
落ちる（1段だけの実装だとここで落ちる）。分岐（`A→B`+`A→C`）と合流（`B→D`+`C→D`）は通る。
`TODO_DEPS_PER_ITEM` 超過 → 400、別イベントの `dependsOnId` → 404。
**読み側は循環データでも終わる**: 直接 INSERT で `A→B→A` を作っても `GET /:id/todos` と
待ちの判定が有限時間で返り、循環に含まれる項目に印が付く（黙って隠さない）。

### 9.4 担当者（2.3 の4通りを1つずつ）

- staff でない人の指定 → 400 `todo_assignee_not_staff`
- **除名・降格・退会申請** → `assigneeState === "left"` / `assignee === null` / TODO は残る。
  退会申請が最も落ちやすい（メンバー行が残るので、`event_member` だけ見る実装では
  `"active"` のまま名前が出る）
- **完全削除** → `assignee_user_id` が NULL に落ち `"unassigned"`。TODO は残る（`SET NULL` の証拠）
- `assignable` に退会申請中・未確定・participant が含まれない
- **アカウント統合**の後、担当が勝ち側に付いている（5. の証拠）

### 9.5 複製（7.）

題名・補足・依存の辺（**複製先の id を指す**）がコピーされ、日付・担当は NULL、
状態は `open`（複製元で `done` でも）。複製元は変わらない。

### 9.6 期限切れ・待ち・ガントの layout（`lib/todoGantt.test.ts`）

- サーバーの応答に `blocked` / `overdue` の**列が無い**（保存していないことを応答の形で担保）
- 遅れの境界: 期限が今日ちょうどは遅れではない。昨日は遅れ。`done` は遅れではない
- 待ち: 依存先が1つでも `open` なら待ち
- 窓の外れ値（年の打ち間違い1件）が列数を爆発させず一覧に落ちる。日付の無い項目は
  帯にならず、`starts_on` NULL は `due_on` 1日の帯になる
- 今日の線・週末の網掛け・線の座標が帯の端に一致すること

### 9.7 フロント（表示だけ）

**絞り込みのテストは書かない**（#383 9.11 と同じ。書くと絞り込みの契約がサーバーと
画面の2か所になる）。フィルタのチップで一覧が絞られること、「担当者が外れています」が
出ること（**名前が出ないこと**も確かめる）、遅れの印が出ること。

## 10. やらないこと（範囲の線引き）

- **テンプレートを作らない**（7.1。#364 の結論待ち。#384 と同じ判断）。複製がその役を務める
- **#383 とデータで繋がない**（3.6）。`event_todo.schedule_item_id` を
  **先回りして足さない**。リンクだけ置く
- **#384 の役割タグを作らない。** 担当は**1人だけ**。複数人・必要人数・役割（受付・司会）は
  #384 の仕事。`event_todo` に `role` や `required_count` を先回りして足さない
- **依存の種類を増やさない**（SS / FF / SF・ラグ）(3.3)
- **自動スケジューリングをしない。** 先の仕事が遅れても後の日付を自動で押し出さない。
  押し出すと、運営が手で決めた日付を機械が黙って書き換えることになる。
  遅れは印で見せて、動かすかどうかは人が決める
- **クリティカルパスを出さない。** 依存が1種類・日付が手入力の段階では
  「いちばん長い経路」以上の意味を持たない
- **進捗率を持たない**（3.7）。細かくしたければ TODO を分ける
- **ドラッグで日程を変えない。** v1 は日付の入力欄。ドラッグは DOM 計測を持ち込み、
  8.3 の「layout は DOM を測らない」を壊す
- **通知・リマインダーを出さない。** 担当に指定したことを通知すると、
  **題名が `notification` に焼き込まれる**。その人が後で staff を外れても通知は残るので、
  **スタッフ専用の内容がスタッフでない人の画面に残る**。期限のリマインダーは
  定期実行の枠が埋まっている（メール構成の制約）。
  将来足すなら、**通知本文に題名を入れず**「TODO が割り当てられました」＋リンクだけにすること
- **横断（全イベント）の「自分の TODO」画面を作らない**（8.4）
- **参加者に一部だけ見せない。** 見え方の軸を2値から増やすと 3.5 の閉じた形が崩れる。
  必要なら一斉連絡 (#172) かイベント詳細の説明文で足りる
- **添付・チェックリスト・コメント欄・サブタスク（階層）を付けない**（階層は依存で表現できる）
- **監査ログを足さない。** タイムテーブルの編集と同じ扱い
- **相対日数での複製をしない**（7.2）。実際に複製が使われてから判断する

## 11. 設計からの差分（実装・相談・実機で変えた判断）

- **見せ方は P1 / G1 / D3 に決定**（8. 冒頭の表。相談で決めた）
- **ガントの窓のフォールバックを追加**（8.3。実装後のレビューで発覚）。日付を持つ項目の
  すべてが窓（120日）より長いとき、最も早い開始日に窓を置いて**帯を窓の端で切って描く**。
  切った項目は `clippedIds` で返し、画面が「帯は途中まで」と注記する
- **完了 TODO の見せ方を実機で調整**（#400 → PR #402）。`done` にした行をその場に残し
  （一覧から即座に消さない）、フィルタをガントにも効かせる
- **日付の加減算は `packages/shared/src/dateOnly.ts` に1本化**。`kpiTrend.ts` が既に
  同じ契約の `addDays` を持っていたので、実装をここへ寄せてあちらから import させた
  （同じ関数を2つ生やすと片方だけ直る）
- **CHECK 制約の位置**（4.1）。期間の逆転を止める CHECK は表単位の制約で、
  列定義の途中に置いた最初の版は SQLite が構文エラーにした（列を書き終えた後ろに置く）
- テストの置き場: `staff-todo.test.ts` / `staff-todo-sql-audit.test.ts`。SQL の切り出しは
  `test/lib/sqlScan.ts` に寄せて #383 の監査と共有した（写し取ると片方だけ緩む）。
  `user(id)` 参照列の登録漏れを機械で捕まえる `merge-user-columns.test.ts` (#396) も
  この実装と同時に入った
