# コミュニティとイベントごとの Discord / Slack 通知（Webhook）

- オーナー決定: kojira 2026-11-13
- 実装: migration `0127_webhooks.sql`、`apps/server/src/lib/webhooks.ts`（送る中身・送り方）、
  `apps/server/src/db/repositories/webhooks.ts`（保存・宛先の解決）、`apps/server/src/routes/webhooks.ts`（設定API）、
  画面は `apps/web/src/components/WebhooksCard.tsx`

## 1. 何をするか

運営が登録した Discord / Slack の Incoming Webhook へ、次の3つを知らせる。

| 種類 | いつ送るか | 送らないとき |
|---|---|---|
| 問い合わせ (`inquiry`) | イベントへの問い合わせが作られたとき、と、問い合わせた本人が続けて書いたとき | 運営（スタッフ）の返信。運営あての「アプリ全体の問い合わせ」（イベントなし） |
| 参加 (`join`) | 本人が参加登録したとき（確定・抽選の申込・キャンセル待ちのどれでも。結果の状態を載せる） | 既に参加済みでの再送信。繰り上げ・抽選の当選は**今回は送らない**（§6） |
| キャンセル (`cancel`) | 本人が参加を取り消したとき | 運営によるロール変更・削除（本人の操作ではない） |

## 2. 登録の単位と、誰が登録できるか

- **コミュニティの Webhook**: そのコミュニティが主催するイベントと、**承諾済みの共催**イベント
  （`EVENT_COMMUNITY_LINKS`。docs/event-cohost.md §6.1「共催も主催と同じ立場」）で送る。
  登録・変更・削除・テスト送信はコミュニティの owner/admin（`communitiesRepo.isManager`）。承認待ちの共催では送らない。
- **イベントの Webhook**: そのイベント1つだけで送る。登録はそのイベントの運営（`requireEventRole(["staff"])`、
  共催の申請と同じ認可）。主催と共催の運営が同じチャンネルを見たいときは、イベントの運営がそのチャンネルを登録する。
  共催先コミュニティの owner/admin にイベントの権限は渡さない（共催は権限を渡さない、docs/event-cohost.md §6）。
  共催先は自分のコミュニティの Webhook で共催イベントも受け取れる。
- **共催先への送信範囲（オーナー決定 2026-11-14）**: 共催先コミュニティの Webhook にも、主催と同じくすべて（限定公開・招待限定のイベント、問い合わせの全文を含む）を送る。
  理由: 「共催は立場として同じ」。イベントの中身をアプリで見るのは、主催・共催のどちらの運営も**そのイベントのスタッフに設定された人**（従来どおり）。
  Webhook の宛先チャンネルはそのコミュニティの owner/admin が登録したもので、登録者の責任で共有する。アプリの閲覧権限（eventViewSql）は変えない。
- 1つの Webhook ごとに、送る種類（問い合わせ・参加・キャンセル）をチェックで選ぶ。既定は全部オン。
- 上限: コミュニティ・イベントそれぞれ 10 個。

## 3. 受け付ける URL（SSRF 対策）

URL の形で Discord か Slack かを決め、それ以外は受け付けない。`https` のみ、ホストは完全一致。

- Discord: `https://discord.com/api/webhooks/<id>/<token>`、`https://discordapp.com/api/webhooks/<id>/<token>`
  （`ptb.` / `canary.` も可）
- Slack: `https://hooks.slack.com/services/<T>/<B>/<secret>`

ポート・認証情報・クエリ以外の余計な部分（`#` など）は拒否する。

## 4. URL の保存と表示

- URL はトークンそのもの。D1 に平文で保存する（アプリにシークレット暗号化の仕組みが無く、D1 にアクセスできる者は
  ほかの秘密〔セッション等〕も読めるため、暗号化しても守れる範囲が増えない）。
- **保存後は API で一切返さない。** 一覧では「種類・ホスト・末尾4文字」（例 `discord.com …a9Xz`）だけを返す。
- ログに URL を出さない。失敗の記録（`last_error`）は HTTP ステータスと短い理由だけ。

## 5. 送り方

- 参加・キャンセル・問い合わせの処理は待たせない（`deferBackground` = `waitUntil`）。
- 宛先: コミュニティ（主催＋承諾済みの共催）とイベントの Webhook のうち、その種類がオンで有効なもの。
  **同じ URL が複数登録されていても1回だけ送る**（URL で重複を除く）。
- 1件あたり最大3回。`429` は `Retry-After`（最大5秒）を守り、それ以外の失敗は 0.5 秒・1 秒あけて再送。
  送れた／失敗の結果を行に残す（`last_sent_at`、`fail_count`、`last_error`、`last_failed_at`）。
- 失敗は2種類に分ける。
  - **送り直しても直らない失敗**: `400` `401` `403` `404` と転送（`3xx`。転送は追わない）。Webhook が
    消された・URL が違うときに出る。これだけを `fail_count` に数え、**5回続いたら**自動で止める
    （`active = 0`）。画面に「停止中」と最後のエラーを出し、「再開する」で戻せる（`fail_count` を 0 に戻す）。
  - **一時的な失敗**: `429`・`5xx`・通信エラー。`last_error` と `last_failed_at` に残すだけで、
    `fail_count` には数えない（止めない）。参加と取消を繰り返して相手に `429` を返させる、Discord / Slack の
    短い障害、のどちらでも通知が止まらないようにするため（レビュー F2）。
- 成功すると `fail_count`・`last_error`・`last_failed_at` を消す。
- 永続のキューは使わない（既存のキュー・cron に乗せない。取りこぼしても運営の通知・ベルは別にある）。

## 6. 中身（日本語）

- 参加: 「参加: <イベント名>」。名前（表示名＋ @ハンドル、プロフィールへのリンク）・状態（確定／抽選申込／キャンセル待ち）・
  参加者数（確定）・イベントへのリンク・時刻。
- キャンセル: 「キャンセル: <イベント名>」。名前・参加者数（確定）・リンク。
- 問い合わせ: 「問い合わせ: <イベント名>」。件名・**本文の全文**・問い合わせた人・運営用のスレッドへのリンク。
  - Discord は embed の説明欄（4096字）に入るだけ入れ、溢れたら次の embed に続ける（1メッセージ 10 embed、合計 6000 字まで）。
  - Slack は section ブロック（3000字）に分けて並べる（50 ブロックまで）。
  - それでも入らない長さは末尾を切り「続きはこちら」とスレッドへのリンクを付ける。
- メールアドレスは載せない。
- 繰り上げ・抽選の当選を送らないのは、本人の操作ではなくサーバーの処理の中で起き、送る場所が多くなるため。
  必要になったら同じ `dispatchWebhooks` を呼び足す。

## 7. テスト送信

「テスト送信」は登録済みの Webhook へ「events lab からのテスト送信です」を1回だけ送り、結果（成功／HTTP ステータス）を返す。
テスト送信の失敗は自動停止の回数に数えない。

## 8. データ

`webhook(id, scope, community_id, event_id, kind, url, label, notify_inquiry, notify_join, notify_cancel, active,
fail_count, last_error, last_failed_at, last_sent_at, created_by, created_at)`。`created_by` は user を参照する（統合で勝ち側へ付け替え、
退会の完全削除では SET NULL）。コミュニティ・イベントが消えたら CASCADE で消える。

## 9. 入れていないもの

- 参加者本人や一般の人の Webhook 登録、任意の URL（Discord / Slack 以外）
- 送信の履歴一覧、リトライの永続キュー
- 繰り上げ・抽選の当選、運営による削除の通知
