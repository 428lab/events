# 確定した日程を日程調整に戻す

状態: **ユーザー承認待ちの提案。実装・配備は未承認。**
調査基準: `1f13ae3cb5008686516a8420546b167a770cad49`（調査時の remote main / staging / production）。
既存の自動参加登録の正本は [schedule-auto-registration.md](schedule-auto-registration.md)。本書は「調整へ戻す」と再確定に伴う差分のみを扱う。

## 利用者に提案する動き

1. 主催者が **イベント管理 → 日程調整**（`/events/:id/manage#date-poll`）を開く。
2. 確定日時の下の **「日程調整に戻す」**を押す。結果集計を開かなくても見える位置に置く。
3. 小さな確認で次を伝える。
   > 日程調整に戻しますか？候補日・回答・参加登録はそのまま残ります。回答者と参加登録者にお知らせします。
   - 募集締切があるときだけ追記: **「募集締切も解除します。再確定後に設定し直してください。」** 日時も表示して、解除対象を明確にする。別画面で先に解除する手間は要求しない。
   - 終了済みなら追記: **「日程未定となり、通常の参加受付に戻ります。」**
   - ボタンは「キャンセル」「日程調整に戻す」。実行中は二重送信を防ぎ、失敗時は閉じずに理由を表示する。
4. 同じ管理セクションで候補日と既存回答が展開され、追加・回答変更・再確定ができる。情報ページには回答用UIだけを出し、管理操作は移さない。
5. 日程を再確定すると既存の日程確定・参加登録結果画面へ進む。再確定確認には **「既存の参加登録は、×・未回答の人も維持します。参加を取り消す場合は参加者一覧で確認してください。」**を補足する。

**推奨: 回答も参加者もリセットしない。** 旧日程で自動登録された人が新日程では×でも、勝手に取消・降格しない。○/△を付け直すことも強制しない。参加者本人による回答見直しと通常の参加取消を使う。回答前の自動登録・匿名でも登録後は名前が出る説明は維持する。

## データ・対象

- `scheduling: false → true` と `access_revision + 1`。日時は旧値を**未確定の内部値として保持**し、NULL/0への書換えや架空の日付を作らない。日程表示は `scheduling` を優先し「日程調整中（開催日時は未定）」にする。再確定で選んだ候補の日時に置換する。
- 候補日・回答（初回回答日時も）・メンバー・参加枠/定員・Entry/EntryMember・採点・出席・タイムテーブル・アンケート・画像を一切削除/リセットしない。旧日付入り画像は自動上書きせず、管理で「画像に以前の日付がある場合は変更してください」と編集リンクを表示する。再確定時の既存画像再生成提案は維持する。
- 旧受領記録/登録結果は戻す時には保持する。管理で「前回の日程確定時の参加登録結果」として閲覧可能にし、現在の参加状況ではないと明記する。次回確定で置換する現行契約を変えず、履歴保存機能は作らない。
- `scheduleAnonymous` / `scheduleVisible` は保持。調整中は結果非公開設定にかかわらず回答UIを表示する現行契約。匿名でも本人の選択が選択済み表示になる。
- 候補のない日時直接指定イベントも対象。「戻す」後は空の候補一覧と候補追加UIになる。旧日時を勝手に候補に追加しない。
- 下書き/公開/アーカイブの状態・visibilityは変えない。開始済み/終了済みという新たな禁止は設けない。現行の日程編集/確定にもその禁止はなく、今回データを壊さないための必須条件ではない。終了判定に依存する表示は調整中へ戻り、既存の結果データは残る。別イベントの作成や大会のリセット機能ではない。
- 再確定時、既存登録者は旧自動/手動の区別なく維持。新規登録は選んだ候補の○/△だけで、取消復活なし、既存の先着順/定員/待機/抽選/複数枠/必須アンケート/終了・締切/退会・閲覧権条件を再評価する。残席は維持した参加者を含めて数える。

## API・原子性（migrationなし）

### 戻す

`POST /api/events/:id/reopen-scheduling`

入力: `{ expectedAccessRevision: number, clearRegistrationDeadline?: true }`。管理画面に表示したrevisionを送る。締切ありの確認には明記のうえtrueを送る。

- 既存event認証/閲覧共通門と `requireEventRole(['staff'])` を通し、書込SQLでもactiveManagerSqlを評価する。閲覧不可は既存同様404、閲覧可能だが管理不可は403、書込時の権限変更は409。
- 同一D1 batchで、revision一致・`scheduling=0`・締切なしまたは解除確認済みを条件に通知INSERTとイベント更新を行う。通知の一括INSERTを先、同じ条件のUPDATEを最後に置き、batchの原子性で片方だけ成功させない。期限解除はUPDATE内で行う。Workerで読んだ人数/権限に依存して一人ずつ書かない。
- 締切ありで解除確認なしは409 `deadline_clear_confirmation_required`、revision不一致は409 `schedule_changed`。いずれも更新せず再読込し、変更された締切を再確認させる。別タブで締切が追加された場合も黙って消さない。
- 成功は200 `{ event }`。同じrevisionの再送は、現在が調整中かつrevisionがちょうど+1なら200で現在状態を返し、通知/更新を重ねない。それ以外の古い要求は409。既に調整中の最新revisionによる要求も無変更200。再確定後に遅れて届いた戻す要求で二度目の再開をしない。

### 確定・編集との競合

- 既存 `POST /finalize-date` の入力に `expectedAccessRevision` を必須追加。ready SQLでrevision一致を確認する。古い画面からの確定が再開後の回答を勝手に締め切るのを防ぐ。
- 確定済みの再送は同候補のreceiptがあり、現在revisionが要求+1のときだけ保存済み結果を返す。別候補や別サイクル/他更新後は409として再取得する。新サイクルの明示確定だけが既存のreceipt置換・登録・通知を実行する。権限確認は再送でも省略しない。
- `eventsRepo.update` は現にrevision条件で書くが、通常の日時/締切変更ではrevisionを増やしていない。**日時・締切・schedulingが実際に変わるPATCHもrevisionを増やす**。日程関連PATCHは画面読込時のexpectedAccessRevisionを要求し、repo内の最新状態でも締切/日時制約を検証する。古い編集フォームで再開直後に旧日時や締切を上書きする競合だけを対象にする。その他項目の編集契約は変えない。
- 調整中→直接日時設定という既存編集経路は維持する（候補確定の自動登録とは別経路）。旧receiptがその直接設定の再送結果と誤認されないよう、直接日時・scheduling変更では旧receiptを同じbatchで無効化し、旧登録結果も現行CASCADEで除く。メンバー/Entry等には触らない。
- 追加カラム/テーブル不要。必須入力追加後の古いクライアントの確定/日程編集は400となり、再読込を案内する。未知の入力を黙って無視して旧挙動へ落とさない。汎用undo・操作履歴・世代テーブルは導入しない。

## 通知・権限・UI整合

- 戻す時は、回答者 ∪ 取消以外の既存メンバー（重複除去、実行者を除く）のうち、現在閲覧できる有効ユーザーへアプリ内通知を一度送る。旧日程で手動参加した未回答者にも届く必要があるため回答者だけにはしない。
- 既存 `info` 種別を用い、公開イベントでは「日程調整を再開しました」「『イベント名』の日程が未定になりました。候補日への回答をご確認ください。参加登録は維持されています。」、リンクは `/events/:id`。非公開/限定公開は既存日程通知にならって内容を汎用化し、タイトル/本文にイベント名や日付・回答者を出さない。event_idを保存し、SQLのeventViewSql、配信時の既存認可を使う。
- メールは既存の設定/認可を尊重しbest-effort、上限50件。通知INSERTには要求固有の識別可能なID群を使い、その今回分だけを配信する。メール失敗で日程を巻き戻さず、HTTP再送でメールを再送しない。フォロワー通知は増やさない。
- 再確定通知の対象も回答者 ∪ 非取消メンバーにする（現状は回答者中心）。既存登録者への本文にも登録維持・必要なら本人取消を記す。新規登録者への登録結果通知の条件は従来どおり。取り消した過去通知/送信済メールを削除・回収しない。
- 現行GETのmyRoleは実メンバーのroleであり、サーバーの管理者相当権限とは一致しない。日程の入口だけを整合させるためGETイベントに `canManageSchedule`（既存isEventManagerに基づくboolean）を追加する。管理ページはstaff以外の既存管理者にも日程セクションだけを表示し、SchedulePanelの管理操作へ渡す。他の管理セクションの権限を広げない。私的イベントへの招待のみ可能な利用者に日程権限を付けない。
- 成功後は event / eventSchedule / scheduleRegistration / 関連イベント一覧・マイページの既存queryをinvalidate。本人回答をサーバーから再取得する。競合は「日程が更新されています。最新の内容を確認してください。」と再取得し、操作を自動再実行しない。
