# 編集画面（スライド / 配信セット）を責務ごとに分ける (#466)

- ステータス: **実装済み**（スライド編集は PR #468、配信セット編集は本ドキュメント
  と同じ PR）
- 対象: `apps/web`（`DeckEditorPage` / `LiveSetEditorPage` とその配下、
  `lib/editor/`、`lib/deckSlides.ts`、`lib/liveScenes.ts`）
- 前提: #466 は「1ファイル 800 行まで」の掃き出し。同じ方針で `EventDetailPage`
  を分けた PR #467 が先にマージ済み

---

## 1. なぜ分けたか

`DeckEditorPage.tsx` が 1106 行あった。ただ、溜まっていたのは「スライド編集の中身」
ではない。読んでみると**同じ仕掛けが 2 本ある**ことのほうが重い。

スライド編集（`DeckEditorPage`）と配信セット編集（`LiveSetEditorPage`）は、
履歴・自動保存・キーボード・キャンバス幅の計測・四隅リサイズの式・画像の差し込みが
**ほぼ字面まで同じ**だった。片方だけ直しても、もう片方は直らない。実際「まとめる猶予
500ms」「保存を待つ 800ms」「最小 20px」といった数字が 2 か所に散っていた。

なので、行数を削るために機械的に切るのではなく、

1. 2 か所にある契約を 1 つにする（`lib/editor/`）
2. 画面を描かずに確かめられる式を外へ出す（`lib/deckSlides.ts`）
3. 残った描画を、出し分けの条件ごと持って行かせる（`components/Deck*.tsx`）

の順で削った。結果として `DeckEditorPage` は 341 行になった（分けた当時。その後の同時編集・書き出しなどで
2026-11-20 時点で 478 行、`LiveSetEditorPage` は 377 行。どちらも 800 行の上限の内）。
続けて `LiveSetEditorPage`（1035 行）も同じ順で削り、**新しい仕掛けを作らずに
上の 1. を採用する**ことから始めた。採用した時点で履歴・自動保存・キーボード・
倍率・画像・四隅の式・採番の重複が消え、本体は 303 行になった。

## 2. どこで切ったか

**共通の仕掛け** (`apps/web/src/lib/editor/`)。編集対象の型を問わない形にしてある。

| 置き場所 | 何を持つか | なぜ 1 か所か |
| --- | --- | --- |
| `useEditorHistory.ts` | Undo/Redo。積む単位（連続変更を 1 手にまとめる猶予） | 「1 手」の定義が画面ごとに違うと、同じ操作で戻る量が変わる |
| `useAutoSave.ts` | 変更が落ち着いてからの保存。読み込み直後は投げない | 待ち時間と「開いただけで保存しない」の判断 |
| `useEditorKeyboard.ts` | 押されたキーを命令に翻訳。打っている最中は効かせない | 打鍵中に要素が消える事故を、片方だけ直して終わりにしない |
| `useCanvasScale.ts` | 実測幅から表示倍率を出す | 要素の座標を実寸で持つという前提そのもの |
| `useImagePicker.tsx` | 選ばせる・縮める・上げる・失敗を伝える | 「新しく置く」「差し替える」で入口が 2 つあるため |
| `resizeCorner.ts` | 四隅の変形の式と下限、ハンドルの逆補正 | 符号を 1 つ間違えると掴んだ隅と逆側が動く |
| `uid.ts` | クライアント側で振る id | 同上（採番の口を 2 つ持たない） |
| `collection.ts` | 並びの式（差し込む・入れ替える・重なり順・まとめて動かす・写す） | ページと要素の並びは両画面で同じ形。型ごとに書くと結果が食い違う |

**スライド固有**。`lib/deckSlides.ts` は React にも MUI にも依存しない純関数だけを置く。
残っているのはグループの扱い（まとめる・外す・選択の展開・写した側を別のグループに
する）と、置いたばかりの要素の既定値、そして選択の読み取り。
`components/DeckSlideList` `DeckLayerList` `DeckToolbar` `DeckCanvas`
`DeckElementPanel` が描画を持つ。

**配信セット固有**。`lib/liveScenes.ts` も同じく純関数だけ。シーンの名前の付け方
（新規の番号・「〜のコピー」。保存される文言なので、作る人の言語で書く。#364 / PR #692）と、5 種類の要素（文字・画像・カメラ・スライド・
イベント情報）の既定値、背景が単色かどうかの判定。
`components/LiveSceneList` `LiveSceneToolbar` `LiveCanvas` `LiveElementPanel` が
描画を持つ。`ResizeHandles` は両エディタから使う。

## 3. 制約（次に触る人が守るもの）

- **`lib/editor/` に画面固有のものを入れない。** 入れた時点でもう一方が使えなくなり、
  分けた意味が消える。選択が単数か複数かのような差は、呼ぶ側から渡す。
- **並びの式は `lib/editor/collection.ts` に置き、型で書き分けない。** 差し込む・
  入れ替える・重なり順・まとめて動かすは `{id}` と `{id,x,y}` だけで書ける。
  `DeckElement` 用と `LiveElement` 用を別々に持つと、同じ操作なのに画面によって
  結果が違うという壊れ方をする。両画面固有として残ってよいのは、
  グループ（スライドだけ）と置いたばかりの要素の既定値だけ。
- **`deckSlides.ts` / `liveScenes.ts` に React を持ち込まない。** ここが純関数で
  あることが、並べ替えや重なり順を画面なしで確かめられる根拠になっている。
- **ドラッグ中は `content` を触らない。** `DeckCanvas` / `LiveCanvas` が
  一時的なずれだけを持ち、
  指を離した時に 1 回だけ確定する。一手ごとに書き換えると履歴が細切れになり、
  位置を渡し直された react-rnd と実際のドラッグ位置がぶつかって震える。
- **数字を画面側に書かない。** 猶予 500ms・保存 800ms・最小 20px・履歴 100 手・
  写しをずらす 20px は `lib/editor/` の各ファイルが 1 つずつ持つ
  （`useEditorHistory` / `useAutoSave` / `resizeCorner` / `collection`）。
  **2 か所あった状態は解消済み。** 画面側に書き戻すと、同じ操作なのに画面によって
  戻る量や保存の間合いが変わる。
- **`useCanvasScale` の ref を付ける要素は、呼ぶ部品の中で必ず描く。** 条件付きに
  すると最初の 1 回で `ref.current` が null になり、倍率が 0 のまま
  ＝真っ白なキャンバスになる。**エラーが出ないので気づけない。**
  読み込みを待つ必要がある画面は、待つ側（ページ）と測る側（`DeckCanvas` /
  `LiveCanvas`）を別の部品に分ける。そうすれば部品のマウント時＝要素がある時に
  測れる。以前あった `ready` 引数はこの形にしたことで渡す画面が無くなったので
  落とした（渡し忘れられる口を残さない）。**この前提はテストで縛ってある。**
  `useCanvasScale.test.tsx` が両方のキャンバスを「描くページ／シーンがまだ無い」
  状態で描き、それでも測りに行くことを確かめる。測る要素より前に早期 return を
  入れると、ここが落ちる。書いてあるだけでは次に触る人が踏むため。

## 3.1 保存がぶつかったとき（チームのスライド）

- 保存は `useDeckSave`（1本ずつ、失敗したら明示の再試行まで止まる）。編集画面は読み込んだ版を `baseRevision` に添え、保存できた応答の `revision` を次に使う
- 409 `deck_conflict` は「ほかの人が保存した」。`useDeckSave` の `error` で見分け、再試行ボタンではなく「最新を読み込む」（`reset` で読み込み直した中身を保存済みとして受け取る）と「この画面の内容をコピー」を出す
- `useUpdateDeck` は保存のあと `["deck", id]` を取り直さない（保存中に打った文字を古い応答で上書きしないため）
- 詳細と権限は docs/team-participation.md「チームのスライド」
- 同時編集（機能フラグ `deck_live_sync` がオンのチームのスライド）では、409 はこの案内を出す前に `useDeckSync` が合わせ直して
  保存し直す（3 回まで）。それでもぶつかるときと、同期が無いときだけ上の案内になる（docs/team-deck-live-sync.md §7.6）。
  AI が書いている間は `423 agent_writing` で編集できない（docs/agent-deck-token.md「4b」）

## 3.2 並びの位置キー `pos`（スライドだけ）

- ページと要素は、配列の順とは別に位置キー `pos`（`0-9A-Za-z`、32 字まで）を持つ。チームのスライドの同時編集で、並べ替えを「動かしたものの `pos` の上書き」として合わせるため（docs/team-deck-live-sync.md §5.2）。式は `lib/deckPositions.ts`
- **編集のたびに** `withDeckPositions` を通す（`DeckEditorPage` の `editSlides`）。配列の順が操作の意図なので、食い違ったら動いた・足した・写したものにだけ新しい `pos` を振る。保存の直前にも同じ関数を通す（最後の守り）。なので保存される配列はいつも `pos` の順で、公開ビューアは配列の順を見るだけでよい
- **読み込むときは、`pos` が配列の順で増えていれば `pos` が正**（`prepareLoadedContent`）。`pos` の無いもの（導入前のデッキ・取り込み・AI が書いたもの）にだけ振る。取り直しのたびに振り直すと、読み込んだ版が違うタブで同じ id のキーがずれる。`pos` が配列の順で増えていない中身は、`pos` を知らない古い画面が並べ替えたもの。そのときは配列の順を正にして、動いたものにだけ振り直す
- 配信セット（`LiveSetEditorPage`）は `pos` を持たない。`lib/editor/collection.ts` の並びの式は配列だけを扱うまま

## 3.2.1 スライドの削除

スライド一覧（`/decks`）の自分のスライドのカードに「削除」がある（2026-11-27、利用者から「スライドの削除ができない」。サーバーの `DELETE /api/decks/:id` はあったが、画面に入口が無かった）。
確認（「元に戻せません。共有したURLも開けなくなります」）のあとで消す。チームのスライドには出さない（メンバーから消せない。サーバーも 409 `team_deck_delete`）。
配信で使っていたスライドを消すと、開いている配信画面に知らせる（今までどおり）。

## 3.3 書き出し（JSON・PDF）

公開ビューア・編集画面・チームのスライド欄に「書き出す ▾」（`components/DeckExportMenu.tsx`）。チームのスライドはイベントが終わると編集できなくなるので、そのあとはここから持ち出す。

- **JSON**: 公開の取り込み形式 events-lab-deck version 2（`public/deck-import/v2/spec.md`）。`/decks/import` にそのまま取り込み直せる。式は `packages/shared/src/deckExport.ts` の `exportDeckV2`（取り込みの `convertDeckImport` の逆）で、書き出す前に公開の検証 `validateDeckImport` に通す。通らなければファイルにしない
  - 編集画面の中身はそのまま書く（回転・グループ・全部の書体・装飾の省略・小数やスライドの外の位置・空の文字）。取り込み直すと同じ中身に戻り、振り直すのは id と位置キー `pos` だけ（並びは同じ）。書けないのは v2 の上限（60枚・1枚50個など）を超えた分だけ（2026-11-28）
  - 色が `#RRGGBB` でなければ既定色（編集画面の色の選択は `#rrggbb` だけを作るので、ふつうは起きない）
  - ファイルに書き出すときは、画像の相対パス（`/api/decks/...`）は表示中のオリジンで HTTPS の絶対 URL にする。HTTPS にならないもの（手元の http など）は空枠にする（ほかの人が取り込めるファイルにするため）。AI の読み取り（docs/agent-deck-token.md §4c）は src を書き換えない
  - 件数・文字数の上限（60 ページ・50 要素/ページ・文字 10,000）を超える分は切る
- **PDF**: 印刷用の画面 `/d/:slug/print`（`pages/DeckPrintPage.tsx`）。1 ページ＝1 スライドで、用紙をスライドの大きさ（960×540px）にして余白を無くす。書体と画像がそろったら（最長 15 秒待って）一度だけ印刷の画面を開く。PDF はブラウザの「PDFとして保存」で作り、サーバーでは作らない
- 書き出すのは**保存済みの中身**（公開の取得と同じもの）。編集画面では未保存のあいだ押せない

## 3.3.1 PDF から取り込む

オーナー決定 2026-11-20: 取り込めるのは **PDF だけ**。Keynote・PowerPoint・Googleスライドは、PDF に書き出してから取り込んでもらう（画面に案内を出す）。取り込み方は、取り込むときに選ぶ（案 C）。

- 置き場所: `/decks/import`（JSON の取り込み画面）の「PDFから取り込む」欄（`components/PdfImportPanel.tsx`）。スライドの一覧の「PDFから取り込む」はこの欄（`#pdf-import`）を開く。デッキを直接作るのでログインしている人だけ
- **見た目そのまま（既定）**: 1ページを1枚の画像（960×540 の全面）にする。崩れないが、文字は直せない
- **文字を直せる形**: 文字を文字の箱にして、写真・図・線・背景は、**文字を抜いて描いた**ページの画像を一番奥に敷く（文字以外は何も落ちない。変わるのは書体だけ）
  - 文字の取り出しは pdf.js の `getTextContent`。同じ行のすぐ隣の切れ端を1行に、左端がそろって詰まった同じ書式の行を1つの箱にまとめる（`lib/pdfImport/pdfSlides.ts`。pdf.js に依存しない純粋な式）
  - 書体は名前で3つ（既定・明朝・等幅）に寄せる。pdf.js の `isMonospace` は和文のゴシック（全角が同じ幅）でも立つので使わない。太字・斜体は書体の情報と名前から
  - 色は、文字ありと文字なしの2枚の画像の違うところから拾う。違いが無い文字（スキャンした PDF の検索用の文字など）は、絵に字があるので箱にしない
  - 部首の文字（「⽉」U+2F49 など。日本語の PDF でよく混ざる）は普通の漢字に戻す
  - 斜め・縦書きの文字があるページと、箱が 49 個を超えるページは、そのページだけ見た目そのままにして、終わったときに何ページ目かを知らせる
- 上限は今のまま: 60 ページ（`DECK_IMPORT_LIMITS.slides`）。超える PDF は選んだときに知らせ、取り込む前に「最初の60ページでよいか」を聞く。画像は 1 枚 6MB まで（サーバーの `deckImages`）。1920×1080 で描いて WebP（作れない端末は JPEG）にし、収まるまで画質を下げる
- 流れ（`lib/pdfImport/importPdf.ts`）: 空のデッキを作る（`POST /decks`）→ ページごとに描いて画像を上げる（`PUT /decks/:id/images`）→ 中身を1回で保存する（`PATCH /decks/:id`、作った版を添える）。取り込み専用の保存口は無い。途中で失敗・取り消したら、作りかけのデッキを消す
- PDF はサーバーに送らない。描くのも文字を取り出すのもブラウザの中
- pdf.js（`pdfjs-dist`、古い iOS Safari でも動く legacy 版）は、この欄で PDF を選んだときにだけ読む（`lib/pdfImport/pdfPages.ts` を動的 import。ほかの画面のバンドルには入らない）。CMap・標準フォント・wasm は vite のプラグイン（`vite.config.ts` の `pdfjsAssets`）が `/pdfjs/<版>/` に置く。日本語の PDF は CMap が無いと文字が取れない

## 3.4 プロフィールに載せる・表示回数

- **載せるのはオプトイン**（オーナー決定 2026-11-13、案A）。デッキごとに「プロフィールに載せる」スイッチ（スライドの一覧）。
  載せられるのは、自分の個人のデッキと、自分がメンバーのチームのスライド（公開イベントのものだけ。限定公開・招待限定の
  イベント名やチーム名をプロフィールから出さないため）。
- **「スライドをすべて自動で載せる」**（オーナー追加 2026-11-13、既定オフ）。オンにすると、今あるものもこれから作るものも載る。
  1つずつ「載せない」にしたものは載らない（例外のリスト）。スイッチはプロフィールの「スライド」タブ（本人だけ）。
- 判定は `profileDecks.ts` の `deckShownOnProfileSql` 1か所（載せられる かつ（「載せる」にした または
  （自動がオン かつ「載せない」にしていない）））。一覧のスイッチの状態・公開プロフィールの一覧が同じ式を通る。
  表は `profile_deck`（本人の選択 show 1/0）と `profile_setting`（自動）。どちらもアカウント統合で勝ち側優先、退会で消える。
- **表示回数**は公開ビューア `/d/:slug` を開いたときに1回数える（`POST /api/public/decks/:slug/view`）。イベントの閲覧と同じく
  生IPは持たず、visitor cookie で日ごとに重複を除く（`deck_view_unique`）。表示回数 = 日ごとのユニーク訪問者の合計。
  持ち主・チームのメンバーの閲覧は数えない。一覧・プロフィール・ビューアに「n回表示」で出す。

## 4. 残していること

- **`DeckCanvas` と `LiveCanvas` は 1 つにしていない。** スライド編集は複数選択と
  グループでまとめて動かす仕掛けを持つが、配信セットの選択は常に 1 つ。1 つにすると
  使わない分岐を配信側へ持ち込むことになる。**同じなのは倍率の出し方・変形ハンドル・
  ドラッグの確定の作法**で、そこは `lib/editor/` と `ResizeHandles` にある。
  配信セットに複数選択を入れるときが来たら、その時に寄せる。
- **配信セット編集の要素は一覧を持たない。** スライド編集のレイヤー一覧に当たるものが
  無く、**選ぶ手段がキャンバスしかない**。テストもそのため、幅を与えて描かれる状態を
  作ってから選んでいる（`LiveSetEditorPage.test.tsx`）。
- **キャンバス上の掴んで動かす操作は自動では確かめていない。** jsdom には寸法が無く、
  ドラッグそのものを追えない。式（`collection` / `deckSlides` / `liveScenes` /
  `resizeCorner`）と結線（`DeckEditorPage.test.tsx` / `LiveSetEditorPage.test.tsx`）を
  分けて押さえてある。
